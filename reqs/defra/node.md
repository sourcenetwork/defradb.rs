# `defra.node.start.no_nameservers`: A libp2p node starts when the host lists no DNS nameservers

- **Parents:** ["go.node"]
- **Scenarios:** ["node::resolver::a_libp2p_node_starts_when_resolv_conf_lists_no_nameservers", "node::resolver::a_libp2p_node_starts_when_resolv_conf_does_not_parse"]

A node started with libp2p networking starts, listens and answers requests when the host's resolver configuration (`/etc/resolv.conf` on unix) lists no nameservers, has lines the resolver cannot parse, or cannot be read: `PeerInfo` returns the addresses it listens on and an introspection query succeeds. The file is read as Go's `dnsReadConfig` reads it: a line, or a word of a `search` or `options` line, that the parser rejects is skipped with a warning (`skipping what hickory cannot parse in a resolv.conf line`), and every nameserver, search domain and option it accepts is kept. The file is read as bytes, as Go reads it, so a byte that is not UTF-8 (a Latin-1 comment) spoils only the line it is on and never hides the nameservers on other lines. When no nameserver is left, or the file cannot be opened or read, `/dns`, `/dns4` and `/dns6` addresses resolve through `127.0.0.1:53` and `[::1]:53`, over UDP and TCP, the nameservers Go's resolver falls back to, never a public DNS service; a readable file keeps its search domains and options. The node then logs one warning naming why: `no usable DNS nameservers in the host resolver configuration, using 127.0.0.1:53 and [::1]:53`, with the cause (`no nameservers found in config` when the file lists none). Startup never fails with `no nameservers found in config`. The file is read once, when the node starts: unlike Go, which re-reads it when it changes, a node picks up new nameservers on its next start.
