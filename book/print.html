The Book of Defra

Introduction

The Book of Defra is the developer guide to defradb.rs: the Rust implementation of DefraDB, a local-first, source-available database built around three ideas:

  1. Documents as Merkle DAGs. Every write produces content-addressed blocks (CIDs) linked into a per-document DAG. History is first-class: any past state can be re-materialized, replicated, and verified.
  2. Conflict-free replication. Fields are CRDTs. Two nodes that apply the same set of blocks in any order converge to the same state; replication never needs a coordinator.
  3. A real storage engine underneath. defradb.rs does not run on an embedded KV library with a mutex bolted on. It runs on regolith, an LSM engine with MVCC transactions, server-side merges, commit-ordered logs, per-thread I/O queues, and encryption at rest. defradb.rs implements regolith’s extension traits and keeps every business decision (queries, CRDT rules, access control, migrations) inside ordinary transactions.

What this book covers

Each chapter takes one subsystem and answers three questions: how does it work, where does it live in the code, and why was it built this way. Every claim in this book was checked against the source of the main branch; file paths are given relative to the repository root so you can jump straight to the code.

The book follows the reading order of the system itself:

  • The System: the ownership map, the design doctrine, and one request traced end to end.
  • The Storage Engine: key families, the merge operator, the LSM layout, encryption at rest.
  • Transactions: lifecycle, the commit path, conflict rules and their business logic.
  • Reads and Writes: which read and write mechanisms exist and when each is correct.
  • Documents and CRDTs: the document model, blocks, CRDT types, head sets, the arrival journal.
  • Querying: the GraphQL pipeline, indexes, history queries.
  • Access Control: the Zanzibar engine, document- and node-level policy, external deciders.
  • Threading: thread-per-core workers, the network edge, single-threaded targets.
  • Replication: transports, push/pull sync, provider discovery.
  • Lens Migrations, Events, Memory Reclamation, API Surfaces, Verification.

A note on scope

defradb.rs is the Rust sibling of the Go implementation (sourcenetwork/defradb) and tracks its API surface, HTTP routes, and on-disk formats where compatibility matters (Go-compatibility notes appear throughout the code). The storage engine and the execution architecture described here, however, are native to the Rust implementation.

The System

This part is the map of the whole. Three chapters:

  • Design doctrine: the invariants every change to defradb.rs must preserve, and the reasoning behind them. This is the “why” chapter.

After this part, the rest of the book zooms into each box: the storage engine, then transactions, reads, writes, documents, queries, access control, threading, replication, and the remaining subsystems.

Who owns what

defradb.rs is a layered system with exactly one rule of ownership per layer. The diagram below is the whole story; the rest of this book walks each box. (The participant labelled gents is the reference client workload; read it as “the client”.)

The layers

The client talks to defradb.rs over GraphQL, either over HTTP or through the embedded API. It owns its own agent logic: leases, claims, streaming segments, event consumption.

The network edge is one tokio runtime, held in one place (crates/edge). It terminates HTTP, P2P, the KMS transport, the Orbis, Vera and embeddings clients, and telemetry export. It is the only place in the process where a tokio runtime exists; no data-path crate depends on tokio. The edge also resolves remote inputs: KMS keys, signatures, Vera decisions, embeddings. These are fetched before the transaction that needs them, with single-flight deduplication, batching and caching, because nothing remote may run inside a transaction closure that can re-run.

The thread-per-core pool is where every database decision runs (crates/workers). Each core runs one pinned executor with no task stealing; a task spawned with spawn_local lives and dies on its core. The pool owns query planning, DAG block construction, CRDT rules, index maintenance, ACP decisions, lens migrations, and the business logic that answers each conflict reason.

The trait implementations are defradb.rs code that plugs into regolith’s generic mechanisms: the key classifier (one match on key prefixes), the merge operator (counters, head sets, document part operands, and their touches), the arrival journal’s log layout, the conflict event listener, and the key provider for encryption at rest. regolith’s mechanisms carry no downstream names; they are generic over exactly these traits. In the code the installed set is slightly larger than the diagram: a PrefixExtractor (crates/storage/src/backends/regolith/prefix.rs) for prefix bloom filters, and TransactionHooks for per-transaction telemetry.

regolith’s DefraLevel mechanisms are the transactional vocabulary: key classes, blind merges, projected reads, validated scans, commit-ordered append, Db::allocate, write-free transactions, transact with typed conflict reasons, and the commit receipt. Everything with the word “transaction” in it lives here, not in defradb.rs.

regolith’s engine serves every user of regolith, not just defradb.rs: memtables, the WAL, SSTs and the manifest, the compaction worker (the only threads regolith starts; defra’s pool places and classifies them), lock-free regolith::sync primitives, and encryption at rest that seals every SST block, WAL record and manifest batch with an AEAD while values stay plaintext inside the engine.

The device is whatever regolith::env provides: real disks, OPFS in the browser, or an in-memory environment for tests.

The boundary, in one sentence

defradb.rs owns what each operation means; regolith owns how transactions stay correct. Every coordination problem (validation, conflicts, retries, ordering, allocation, durability) is a regolith mechanism; defradb.rs never adds a lock, a retry loop, or a guard around storage. That boundary is the load-bearing wall of the architecture, and the next chapter is about it.

Design doctrine

Every subsystem chapter in this book ends with a “why”. This chapter collects the rules that produced those answers. They are not aspirational: they are enforced rules of the repository, written down for every contributor and checked in review.

The engine owns the transaction

regolith, run at IsolationLevel::DefraLevel, owns everything transactional: validation, conflicts and their reasons, retries, merges, commit-ordered append, ID allocation, the commit receipt, and encryption at rest. defradb.rs implements regolith’s traits (KeyClassifier, MergeOperator, LogLayout, EventListener, KeyProvider, PrefixExtractor, TransactionHooks) and calls its methods.

The consequence is a negative rule with real teeth: defradb.rs carries no transaction mechanics. No lock around storage, no retry loop, no read outside a transaction feeding a decision inside it, no key-layout trick to dodge a conflict, no pending state, no second commit, no guard. A conflict problem is solved by a regolith mechanism. Changes only ever remove coordination from defradb.rs, never add it.

Why. Every lock, retry loop and guard is a second implementation of something the engine already does, and the two copies drift. The history of this codebase includes a shared transaction mutex, per-document write queues, an arrival guard, a batch gate and eleven retry loops; all were deleted, one measured step at a time, and the engine’s own mechanisms replaced them; the plan that deleted them, step by gated step, is recorded in the repository’s docs.

Pick the mechanism by what the decision depends on

The reads-and-writes rules are the heart of the design, and each chapter of this book instantiates them:

  • A decision on a whole value: get (an Ordinary key), validated at commit. An identical rewrite is not a change.
  • A decision on some parts of a document: get_parts(key, parts), validated only against writes that touch those parts. Disjoint parts of one document never conflict.
  • Traversal hints that decide nothing (HNSW neighbours, head sets): get_parts(key, &[]), never validated.
  • A decision on what exists in a range (ACP tuples, a claim queue): a validated scan, so a write inside the range aborts the decision.
  • Writes that commute (blocks, head sets, document part operands, secondary index entries, counters, journal appends): blind puts, merges and appends that never conflict.
  • Races that need one winner (unique keys, the DocID mapping, deletion markers, DDL, ACP tuples, the applied key of a remote block): ordinary validated keys whose loss surfaces as a typed Conflict.

Why. A read that validates more than its decision needs is a defect: it manufactures conflicts out of writes that could not have changed the answer. The mechanism is picked so that the set of conflicting writes is exactly the set of writes that change the decision.

Everything with an outside effect is prepared before the transaction

A transaction closure may run more than once. KMS keys, embeddings, signatures and short IDs are computed before transact; nothing remote is fetched inside a closure. An input that depends on the transaction’s own reads ends the attempt, the input is fetched at the edge, and the attempt runs again with the input memoized by its exact request bytes.

Why. Remote calls inside a retried closure are either wasted (fetched again per attempt) or wrong (the answer changes between attempts). Preparing inputs makes attempts deterministic and fast, and a signed or encrypted block is never redone.

Lock-free, thread-per-core, one network runtime

Synchronization comes from regolith::sync (atomics, lock-free maps, queues, channels). The final code has no std::sync::Mutex and no std::sync::RwLock anywhere in the workspace, and lints reject holding a lock across an .await. Shared values are immutable snapshots swapped atomically; data moves between threads as messages, never as shared memory. Every core runs one pinned executor, no task steals, and the network lives on one tokio runtime at the edge. The Threading part is the full story.

Why. Throughput and tail latency. A mutex on the data path serializes cores that have nothing to do with each other; task migration wrecks caches and makes wakeups cross cores; a second runtime makes shutdown and ordering undefined. The engine’s per-thread I/O queues only work if a thread’s completions arrive on that thread, which requires the task to still be there.

Business logic owns the meaning of each conflict

A conflict is not an error to hide: regolith returns it with a reason (whose write won, on which key, at which sequences), and defradb.rs decides what it means. An already-deleted document is a no-op; a changed part re-runs the decision on the new value; a lost unique-key race is reported to the client; a revoked ACP tuple denies the write; a changed definition re-runs against the new one. One retry policy for every attempt, from configuration, through one function.

Why. Only the business layer knows whether a lost race is an error (the user’s compare-and-set failed), a retry (re-decide on fresh data) or a success (the delete already happened). The engine cannot know; the client must not have to.

Nothing valid is rejected

A clean refusal is not a safer wrong answer. A request the product is supposed to serve is served; if the wiring is missing, the wiring is the work. “Fail loud” governs states the system cannot know (corruption, missing configuration), never features.

Formal models beside the code

No logic change without its models: temporal and concurrent behaviour gets a TLA+ model, data structures and merge laws get Lean proofs, both written before the code and both run in CI. The Verification chapter maps mechanism to model.

Why. The invariants here (convergence, ordering, exactly-once, no public window for ACP) are exactly the class of property that testing cannot establish and model checking can. The ELI5 rule for proof files (every line explained in plain words) keeps them useful to every developer, not just the author.

A request, end to end

This chapter traces one GraphQL mutation, an update of a single document, from the client to durable, visible state and back. It is a preview of every mechanism in the book; each step links to the chapter that covers it in depth.

The numbered steps below follow the diagram.

1. In, and routed at the edge

The client sends the mutation over HTTP (or the embedded call path). The network edge, the one tokio runtime, parses only what routing needs: which document (if exactly one) a mutation names. Everything else about the query is parsed and planned on a worker of the pool, routed once, here, at the edge. A mutation naming exactly one document goes to that document’s core, so its writes and merges run one at a time; everything else goes to the least-loaded core (crates/query/src/pooled/route.rs, crates/workers/src/pool/routing.rs). No request hops from core to core.

2. Prepare outside effects

Before any database worker is involved, the caller (the edge task) prepares everything with an effect outside the transaction: KMS keys, embeddings, signatures, short IDs. Only then is the prepared work submitted to the pool (crates/query/src/runner/prepare.rs). A transaction closure may run more than once, so anything with an outside effect must already be in hand. Remote inputs that depend on the transaction’s own reads end the attempt, get resolved at the edge (single-flight, batched, cached), and the attempt re-runs with them memoized.

3. The transaction

transact begins at a snapshot and runs the closure. Inside, the worker:

  • reads only the parts it decides on: get_parts(doc, parts the filter and the indexes use), a projected read validated against writes to exactly those parts (Reads);
  • checks ACP with validated reads of the tuples the decision relies on (ACP inside the transaction);
  • writes field operands as blind merges, index entries as blind puts and deletes, and, when the document is new, appends to the arrival journal with the document as its once key (Writes).

4. Commit

commit_nowait validates against a sampled horizon, then checks only the delta under the critical section, and returns a ticket. The task awaits it while its core runs other tasks: a commit group’s fsync is a claimable unit on every member’s IoQueue, run by the first member core to poll it. The completion arrives on this core’s own queue: durable and visible, with a receipt carrying the commit sequence (The commit path).

5. The conflict branch

When the commit loses a race, regolith returns a Conflict with the key, both writes, and their sequences; the event listener records telemetry; and transact re-runs the closure with the reason. Business logic decides what the reason means: re-decide on fresh data, report the lost race to the client, or turn it into a no-op (Conflict business logic).

6. Out

On success, the response returns to the edge, and events are published in commit-receipt order (CommitReceipt.seq), so subscribers see writes in the order the engine made them durable (Events).

Why this shape. Every wait in the path is an .await on something the worker’s own core completes: the commit ticket, an I/O wait, an input event. The core is never blocked, never idles when it has runnable tasks, and is never woken when busy. That is the threading contract in one request.

The Storage Engine

defradb.rs stores everything in one engine: regolith, an LSM-transaction engine that defradb.rs does not fork or wrap with adapters. It is opened directly, configured per target (server, embedded, wasm, memory), and extended through traits that defradb.rs implements (crates/storage/src/backends/regolith/).

This part covers the engine-facing surface a defradb.rs developer works with:

  • Keys, families and classes: the byte-level layout of every key defradb.rs writes, and how the classifier maps key prefixes to the engine’s behavioural classes.
  • The merge operator: how counters, document parts, head sets and vector index records merge blindly and associatively inside the engine.
  • LSM structure: what actually lands on disk (WAL, SSTs, manifest), how compaction runs, and how memory is bounded and reclaimed.
  • Encryption at rest: AES-256-GCM-SIV sealing of every file, keys from a KeyProvider, values plaintext inside the engine.

The transactional mechanisms the engine provides on top (transactions, conflicts, append, allocate) are covered in the Transactions part.

Keys, families and classes

Every byte defradb.rs writes has a family, and every family has a class. The class decides how the engine treats the key: whether writes to it conflict, whether reads of it are validated, whether identical bytes are the same write. This chapter is the complete map.

The key classes

regolith defines four behavioural classes; defradb.rs assigns each key family to one by implementing KeyClassifier (crates/storage/src/backends/regolith/classifier.rs):

  • Ordinary: last-writer-wins keys. A read of an Ordinary key inside a write transaction is validated at commit (an identical rewrite is not a change), and two different puts of the same key race; one wins.
  • ContentAddressed: the key is the content’s hash (a CID). Identical writes are literally the same bytes, so both commit; different bytes under one block key are rejected. A read that found the key is validated only for removal.
  • Log: a commit-ordered, engine-assigned append-only sequence. Writes never conflict; the engine assigns positions in commit order (the arrival journal).
  • CommutativePrefix: keys whose writes commute within a prefix, so a scan of the prefix is not recorded as a validated range. (defradb.rs’s families are classified Ordinary, ContentAddressed or Log today; the class exists in the engine’s vocabulary and appears in the read rules.)

The classifier is one lookup: it finds the key’s family in a static table (families::family_of) and maps the family’s Class to the engine class. A ContentAddressed family key that does not parse as a CID falls back to Ordinary; a key of no family, cut short or malformed, stays Ordinary. Unknown keys are never rejected: they are simply ordinary.

Why head sets are Ordinary, not special

A head set (the set of a document’s current DAG heads) lives under one Ordinary key per document, but its writes are blind merges of a set operand, and its reads are get_parts(key, &[]), which validates nothing. The class of a key is the engine’s default behaviour; the merge operand and the parts mechanism narrow it to exactly what the decision needs. This is the general pattern: the class sets the ceiling of strictness, the mechanism picks the floor.

What the classes buy

The classifier’s tests demonstrate the contract in four sentences (classifier/tests.rs):

  • Two identical ContentAddressed block writes both commit: same CID, same bytes, nothing to race.
  • Two different decisions on one Ordinary key race; the second commit gets a typed Conflict.
  • A decision that read a block (found it) conflicts with a later delete of that block: the read is validated for removal only.
  • Disjoint-part document writes never meet: the operand’s touches says which parts it changed, and a projected read is validated only against those.

Why one static table. Classification is on the hot path of every write and every validated read. One table, ordered longest-prefix-first, is one binary search over a handful of entries, and a 256-entry first-byte index jumps straight to the candidates (crates/storage/src/backends/regolith/families.rs). It also makes the layout auditable: this page is the complete list of what defradb.rs stores.

The merge operator

The merge operator is defradb.rs’s main superpower on top of the engine: writes that commute are expressed as merge operands, so concurrent writers of one key never conflict and the engine folds them in any order. DefraMergeOperator (crates/storage/src/backends/regolith/merge/mod.rs) implements regolith’s MergeOperator under the name "defra-values-v1" and serves every operand kind from one dispatch on a kind byte.

full_merge: applying operands to a base

full_merge decodes the base value, applies each operand in order, and re-encodes:

  • Counters: the base is big-endian and zero-initialized when absent. INT64 uses wrapping addition, so integer counters converge in any order. Floats add plainly, and the counter chapter of the CRDT docs is explicit that float addition is not convergent in general; the engine keeps it deterministic by order.
  • STATS: two big-endian i128 halves, added with overflow checks; an overflow fails the merge rather than wrapping a statistic.
  • DOCUMENT: the base is a stored document (crates/document/src/stored.rs, fields keyed by stable u32 field ID, each with a kind and a priority). Each operand is applied field by field: LWW fields take the higher-priority value (empty bytes with a priority is a tombstone, and the priority survives), counter fields add. The stored format’s magic is DFV\x01.
  • HEAD_SET and the vector kinds dispatch to their own modules, below.

partial_merge: folding operands without the base

The engine can fold operands before seeing the base value (they may arrive in a batch). partial_merge is only allowed where folding is exactly equal to applying in sequence:

  • HEAD_SET operands fold by function composition (below).
  • VECTOR_LINKS fold by concatenation of the 12-byte addition records.
  • A pair of DOCUMENT operands folds only when every field is LWW or an integer counter: a join of LWW fields is associative, and wrapping integer sums are exact in any grouping. Anything else returns “cannot fold”, and the engine keeps the operands.
  • A pair of INT64 operands folds by wrapping addition.

Floats and the checked i128 statistics deliberately never fold: folding a pair could change rounding or hide an overflow that a later base would have surfaced (crates/storage/src/backends/regolith/merge/mod.rs documents the reasoning beside the code).

touches: which parts an operand changed

touches(key, operand, parts) answers: does this operand write any of these part IDs? Projected reads are validated against exactly the operands whose touches returns true:

  • a DOCUMENT operand touches iff one of its field IDs is in parts;
  • a HEAD_SET operand touches iff one of its names hashes to a listed part;
  • a vector operand touches iff it carries the links part;
  • anything malformed or kind-less touches true: the conservative answer, because an operand that cannot be understood must be assumed to change everything.

The operator’s contract is checked beside it with the engine’s own property harnesses (check_merge_operator, check_touches) plus per-kind tests in crates/storage/src/backends/regolith/merge/tests/.

Head sets: state functions that compose

A head set is one value holding the state of many named heads, each name in one of three states: Absent, Ahead (a parent seen before its child arrives) or Live(priority). Writes are per-name state functions (crates/storage/src/backends/regolith/merge/head_set.rs):

Each operand stores, per name, the images of the three states (a function on three points). Composition of these functions is associative, which is exactly why partial_merge may fold any grouping: folding by function composition equals applying in sequence. Names are stored sorted, so folds are one walk of two sorted lists, and the encoding is canonical.

Each name is one part: part(name) = NAME_PART | rapidhash(name). A publication that decides on some heads (their names) is refused only by operands that touch those names, so a document publishing a new field head does not conflict with a concurrent publication of a different field.

Why state functions instead of read-modify-write. The old layout kept one key per head and read before writing, which made every publication a race on a growing set of keys. Encoding the transition as a value (a function that says what to do in every state it may find) turns the whole update into one blind, order-independent merge. The “ahead” state exists so a child block arriving before its parent records the gap and the parent’s later arrival consumes it, exactly once.

Vector index records

HNSW graph maintenance uses the same trick at the node level (crates/storage/src/backends/regolith/merge/vector.rs): links(layer, neighbour) is a 12-byte addition record; full appends the neighbour to that layer’s sorted, deduped list. Two structural rules are enforced in the operator: a blind addition never raises a node’s height (height is structural, chosen at insert), and self-links are refused. counts(live, waste) adjusts approximate rebuild counters with saturating arithmetic so advisory statistics never wrap. Reads of these records are advisory (get_parts(key, &[]) or a single part), so graph maintenance never conflicts with queries.

Why the operator owns structure rules. If blind merges could corrupt the graph (raise a height, add a self-link), commutativity would be worthless: concurrent maintenance would need locks. Pushing the invariants into the operator makes the blind path the safe path, and the invariants are proven in Lean beside it.

LSM structure: WAL, SSTs, compaction

regolith is an LSM engine: writes land in a memtable protected by a WAL, memtables flush to SST files, and compaction merges SSTs in the background. defradb.rs does not reimplement any of this; it configures it and reads its telemetry. This chapter is what a defradb.rs developer needs to know about what is underneath.

Opening a store

RegolithStore::open_with_options (crates/storage/src/backends/regolith/store.rs) is the single entry point:

  1. Engine options are assembled in crates/storage/src/backends/regolith/config.rs: the merge operator, the prefix extractor, the at-rest key provider, statistics, and the store’s event listener and transaction hooks.
  2. On native targets the open path first checks for a legacy per-value-encrypted store and, if found, performs the one-time rewrite to the file-sealed format (rewrite/), streaming in bounded batches; then opens OptimisticTransactionDb::open.
  3. On wasm, OPFS is mounted (with a durability fallback to eventual mode when the browser reports no durable sync).
  4. The classifier and isolation level are attached to the handle.

Configuration profiles (crates/storage/src/backends/regolith/config.rs):

  • server defaults: DurabilityMode::Immediate, IsolationLevel::DefraLevel, a 30 s close timeout;
  • embedded: engine sizes tuned for a 1-4 MiB working set;
  • wasm: the OPFS environment’s own limits;
  • memory: a MemEnv that starts no threads, so inline compaction is enabled: with no worker, a write that a stall stops runs the compaction itself, or nothing ever clears the stall.

Threads: who runs what

The pool wraps the engine environment with placed_on(pool) (crates/storage/src/backends/regolith/config.rs), which places the threads regolith starts (compaction, log writeback) through the workers pool as background-class threads. That keeps them off the cores running data-path workers and accounted for in one place. An in-memory environment starts none.

The read path

A read consults, in order: the transaction’s own buffered puts, deletes and merges (in operation order), then the memtables, then L0, then deeper levels by binary search. All of it is zero-copy where the engine offers it (defradb.rs reads with get_slice and Bytes::from_owner, so values are borrowed, not copied). Block-cache misses are where CacheOnly and the IoQueue machinery takes over; see Threading.

Writes, WAL and SSTs

A transaction’s writes are buffered in the transaction, not the memtable, until commit. At commit the engine validates, assigns sequences, writes one WAL record for the whole commit group and fsyncs it once (see the commit path). Memtables flush to SST files when they fill; the manifest tracks the live file set. defradb.rs never writes a file itself.

Compaction

A stripe-aware compaction worker merges SSTs in the background. defradb.rs installs no compaction filter, on principle (crates/storage/src/backends/regolith/mod.rs documents the decision): a head-set entry depends on later writes; nothing expires by time alone; a document part’s tombstone carries the priority a late merge is ordered against; index entries, blocks, ACP tuples and guards each decide something until another key says otherwise. A filter that dropped any of them would change what a reader or a later merge sees. Data retirement is a business decision (downsample retention, collection delete), and those run as ordinary transactions; see Memory reclamation.

Statistics and telemetry

Stores keep ticker-level statistics only (StatsLevel::ExceptHistogramOrTimers): a timer would read the clock twice per iterator step, and a histogram sample costs atomics on every read and commit. Every open store exports its tickers as one OTel counter (crates/telemetry/src/engine_tickers.rs), and the store’s EventListener reports flushes, compactions, table-file creation and deletion, background errors, a discarded WAL tail at open, and every commit conflict with its reason.

Why ticker-level only. The observable cost of measurement has to be below the noise floor of the operation measured, or the measurement changes the system. Histograms and timers on per-read paths failed that test; tickers (monotonic counters) do not.

Encryption at rest

defradb.rs encrypts storage in two distinct places, and the difference matters:

  1. Document field encryption (application-level, Go-compatible): individual field values are sealed with fresh AES-256 keys delivered by the KMS; the encrypted payload becomes part of the block’s CID. Covered with the KMS and blocks.
  2. Encryption at rest (engine-level): when at-rest keys are configured, regolith seals every file it writes, so a stolen data directory is ciphertext. Without configured keys the engine does not seal anything. This chapter.

What the engine seals

Every SST block, WAL record and manifest batch is sealed inside its existing frame with AES-256-GCM-SIV, the tag taking the place of the checksum (regolith/src/engine/seal.rs). Values are plaintext inside the engine: byte equality, value-validated reads, ContentAddressed same-bytes checks and merge operators all keep their meaning, because nothing above the file layer ever sees ciphertext. With keys configured, disk (or OPFS) holds ciphertext only; without them, files are plaintext.

This is precisely why encryption lives below the mechanisms rather than above them. The diagram’s upper half records the previous design, a per-value encrypting wrapper above the engine: with a random nonce per value, identical plaintexts differ in bytes, so elision, value-validated reads and content-addressed block identity all broke, and merge operators saw ciphertext, making counters and head sets impossible. That wrapper was deleted, and a one-time rewrite migrates old stores at open (crates/storage/src/backends/regolith/rewrite/).

Where keys come from

defradb.rs implements regolith’s KeyProvider (crates/storage/src/backends/regolith/encryption.rs):

  • current() returns the active key id: the first 4 bytes of a domain-separated SHA-256 of the key material.
  • key(id) returns the key bytes for an id, so old files remain readable after rotation.

AtRestKeys::single(key) seals everything with one key; rotated(current, older) supports rotation with a set of older keys (refusing two distinct keys that share an id, with a birthday-search test proving the check). Compaction re-seals files it rewrites under the current key, so rotation completes as data churns.

Keys enter through the node builders (with_at_rest_encryption_key, with_previous_at_rest_encryption_keys on both the defra-node and embedded builders), and the CLI fetches them from the keyring (crates/keyring: file (JWE), OS keyring, or systemd-creds backends; standard names encryption-key and encryption-key-previous).

What is deliberately not encrypted at rest

The engine seals file contents, not file metadata: the shape of the LSM (file count, sizes, write pattern) remains visible to someone who holds the directory. Field-level encryption is the answer when the existence of a value must be hidden: an encrypted field’s block CID is derived from ciphertext, so the database cannot read it without the KMS, independent of at-rest encryption.

Why AEAD inside the frame. Sealing inside the existing SST/WAL frames means encryption is not a new format: recovery, checksums, tooling and proofs are about the same frame with a tag where the checksum was. GCM-SIV specifically (misuse-resistant AEAD) means a repeated nonce under any bug does not leak both plaintexts wholesale, which is the failure mode you cannot rule out in a long-lived storage engine.

Transactions

Transactions are the centre of defradb.rs, and the centre of the centre is a division of labour: regolith owns the machinery (snapshots, validation, conflicts, retries, ordering, durability), defradb.rs owns the meaning (what each document write is, what each conflict means for the caller).

Lifecycle and states

A defradb.rs transaction is an engine transaction (regolith::Transaction) wrapped in a DbTxn (crates/db/src/txn/mod.rs) that adds the namespaced store views (datastore, blockstore, headstore, systemstore, acpstore, peerstore), a transaction-scoped collection catalog, and the statement savepoint machinery. The state machine it moves through:

Open: reads see own writes, writes buffer

An explicit write transaction begins with begin at a snapshot and is owned by one core for its whole life. Reads inside see the transaction’s own buffered writes and merges in operation order (read-your-own-writes), and put, delete, merge and append are buffered in the transaction, not the memtable. Savepoints can be set, rolled back to, and released, including the per-statement savepoints of an explicit transaction.

A read-only transaction does not begin an engine transaction at all: it pins a snapshot, which is the same view without commit-time validation nothing will ever ask for (crates/storage/src/backends/regolith/transaction.rs).

Validating: the write-free fast path

At commit the engine validates the read set against newer commits. A transaction that wrote nothing and read at one snapshot is write-free: no validation, no critical section, done. This is not a corner case; it is every status read, every query without a mutation, every arrival page. Concretely: a write-free attempt and a concurrent update of the very rows it read both commit (there is a regression test that asserts exactly this, crates/storage/src/corekv/retry/).

Decided, written, durable, visible

A transaction that wrote something and kept every race:

  1. Decided: sequences, log positions and allocations are assigned in group order.
  2. Written: one WAL record for the whole commit group.
  3. Durable: the group’s fsync runs as a claimable unit on the members’ own IoQueues.
  4. Visible: published in sequence order; each member’s completion lands on its own queue; the receipt carries the commit sequence (CommitReceipt.seq).

Conflicted: the re-run

When a key loses its race, the engine returns a typed Conflict, and the owning retry loop (transact) re-runs the closure in a fresh transaction at a new snapshot, handing it the reason. The closure is written to be re-runnable: everything with an outside effect was prepared before it, and its decisions re-derive from the fresh reads. If the business logic stops (a lost unique race reported to the client) or the attempts run out (configured, default 5 re-runs), the transaction is Failed; otherwise it goes back to Open.

Interactive (explicit) transactions differ in exactly one respect: they return their conflicts to their caller instead of re-running automatically, and a failed statement rolls back to its savepoint.

Why re-run instead of blocking. A transaction that waits for the writer it raced holds a thread and a snapshot hostage. Re-running the closure at a fresh snapshot is optimistic concurrency: under contention the cost is a re-derive, not a stall, and the conflict reason usually lets the business logic finish in one re-run (or zero, when the answer is “already deleted”).

The commit path

Two properties define defradb.rs commits: a commit group shares one fsync, and a committing core never blocks the whole core waiting for it. The engine achieves both with a two-stage design that defradb.rs taps into without adding anything in between.

Stage one: group commit

Transactions that arrive together commit together:

  1. Validate against a sampled horizon, outside the critical section. Each committer checks its read set against a recently sampled view of committed sequences; only what the sample cannot answer is left for the critical section.
  2. Inside the critical section: only the delta, plus the write sets of earlier group members, so a transaction cannot conflict with a member already decided in the same group.
  3. Assign in group order: commit sequences, log positions (for appends), and ID allocations.
  4. One WAL write for the whole group.
  5. One fsync, as a claimable unit on every member’s IoQueue: the first member core that polls between tasks claims the unit with one CAS and runs it; a member that would block instead (a pool-less caller) runs it as a blocking commit.
  6. Publish visibility in order; each member’s completion is pushed to its own queue.

The critical section is deliberately tiny: everything expensive (validation against old data, the WAL encoding) happens outside it or once per group.

Stage two: the lock-free pipeline

Past the group stage, the engine’s hot path has no critical section at all. A committer:

  • reserves a ring slot with one fetch_add;
  • finds slots decided in ring order by any thread, through helping: whichever thread reaches an undecided slot decides it, idempotently;
  • writes the decided slot at its offset (any thread, idempotent per key and sequence);
  • advances the durable watermark by fsyncing the written prefix (a unit any waiting core may claim);
  • applies to the multi-writer memtable and publishes the contiguous prefix, pushing each committer’s completion to its own queue.

An aborted slot leaves no hole: no sequence, no log position, nothing published. A committer helps every commit ahead of its own and never waits for another thread to be scheduled; that is the meaning of “helping”, and it is what makes the pipeline lock-free rather than merely fine-grained-locked.

What defradb.rs adds: nothing in between

The store’s module doc states the rule: snapshot capture and native commit use the engine directly, “so independent commits can join its commit groups” (crates/storage/src/backends/regolith/store.rs). On a worker’s IoQueue the commit is commit_nowait and the ticket is completed by that same queue (crates/storage/src/backends/regolith/transaction.rs); without a queue, the commit syncs on the calling thread. Nothing defradb.rs does stands between the caller and the engine’s grouping.

Ordering on top: the commit receipt

Every commit returns a receipt with a sequence (CommitReceipt.seq). defradb.rs uses it as the one ordering token for everything downstream: post-commit callbacks run in receipt order across threads (crates/storage/src/backends/regolith/event_order.rs), and events are published in that order (see Events). A seq is never persisted across a wipe or restore, so ordering promises never span a database replacement.

Why one fsync per group. The fsync is the durable, irreducible cost of a commit; sharing it across the group is throughput that costs nothing. Making the fsync a claimable unit on the members’ own queues is what keeps it off the critical path of any one core: whoever gets to polling first runs it, everyone else’s completion arrives like any other I/O, and a busy core is never woken to do someone else’s fsync.

Conflict rules

The engine applies these rules; defradb.rs picks its mechanisms so that the set of writes that conflict with a decision is exactly the set of writes that could change that decision.

The consequences, in one paragraph each

On document paths, almost nothing conflicts. Field writes are blind merges of part operands; head sets are blind set-operand merges; blocks are content-addressed; the journal is an append. The races that remain are races defradb.rs asks for: one winner per unique index key, per DocID mapping, per deletion marker, per definition, per ACP tuple, per remote-block application, and per claim (two updates of the same parts).

Delete-after-delete is the only conflict left on plain document paths. Two deletes of one document both read it as present; the second’s validated read meets the first’s delete. The business logic answer is “already deleted: success as a no-op”. (A blind delete of an already-deleted key would not even conflict: it is elided.)

Disjoint parts never conflict. Worker 1 updates title, worker 2 updates status: each did a projected read of its own parts, each wrote an operand touching its own parts, touches says the operands do not meet, both commit. This is the mechanism that replaced per-document write queues.

Scans that decide are validated scans. A claim queue, an ACP owner prefix, a collection version scan: any newer write inside the covered range aborts the decision, because the set of keys the decision covered has changed. Scans that merely yield (a query’s document scan) are not validated: phantoms do not matter to a snapshot read, and a key the transaction then writes is validated as a read anyway.

Why identical bytes are not a change. Validation exists to protect decisions, not to enforce an illusion of exclusivity. If the value a transaction would write is byte identical to what is already there, no decision anywhere could observe a difference, and reporting a conflict would be manufacturing an error. The same reasoning elides a delete of an absent key and lets two identical content-addressed puts both commit.

Conflict business logic

The engine says who won; defradb.rs decides what it means. This chapter is the race gallery: each race that can actually occur, and its outcome. Together they are the regression suite for the conflict design: every one of these has a test that pins it.

Two updates of different parts

Both commit. Each worker projected-read its own parts and merged an operand touching its own parts; the operands commute. The document holds both changes, with no lock and no conflict. This is the common case for concurrent work on one document.

Two updates of the same part (a claim)

One wins; the loser’s projected read meets the winner’s operand (mine ReadParts, theirs Merge), and its re-run sees claimed, the filter no longer matches, and the business logic reports “not claimed” to the client. The claim is exactly a compare-and-set expressed as a projected read plus a merge, so it needs no unique key and no lock.

An update against a delete

The delete wins. The update’s projected read (which included the alive part) meets the delete; the re-run finds the deletion marker and reports not-found, re-adding no index entry. Note what did not happen: the update did not resurrect the document, because its decision to write at all was anchored on a validated read.

A delete against a delete

The second reports “already deleted” as a success no-op. This is the only conflict that remains on plain document paths, and it exists because each delete read the document as present; the blind-delete fallback is elided by the engine.

A local create against a P2P merge of the same document

Both sides put identical blocks (content-addressed, no conflict) and both read the DocID mapping as absent (validated). One materializes the document; the loser’s re-run finds the mapping present and applies its blocks as operands only. The arrival journal’s once key (the document) holds one row: the loser’s append finds the once key already applied, so the journal has no duplicate even though both attempted an append.

A write against an ACP revocation

The revocation committed first, so the write’s ACP check (validated point reads and a validated scan of the tuples it relied on) loses its race. The re-run finds the tuple absent and denies. No write ever commits after a revocation it raced: the revocation is just a delete of an Ordinary key inside the validated range of the write’s authorization decision. The full ACP story is its own chapter.

A client lease, in full

The gents workload keeps per-request state as a document: renewal extends expiry, the appender reads state and generation, a client latches an interrupt operand. The interrupt commutes with renewal (disjoint parts, both commit). The appender’s race with renewal is the interesting one: under a lease model where the appender also reads expiry, renewal’s operand touches a part the appender read, and the appender conflicts; once gents decides on generation instead of the expiry deadline, the parts separate and the conflict disappears. This race is documented as the client’s own model requiring it, removable by the client’s lease change, and it is the template for how part design moves conflicts around: what conflicts is what the two sides’ parts share.

The pattern behind all seven

Every race has the same anatomy:

  1. Someone decided, so they read with exactly the validation their decision needs.
  2. Someone else’s write changed what the decision rested on.
  3. The engine reports a typed reason; the loser re-runs with it.
  4. The business logic reads the reason and produces the domain answer: no-op, not-found, not-claimed, denied, or reported to the client.

No locks were taken in any of them. The “lock” is the validated read; the “unlock” is the commit.

Explicit transactions

An explicit (interactive) transaction spans multiple client statements: begin, several queries and mutations, commit or discard. defradb.rs runs each one as an actor on one worker: the transaction is begun on a worker of the pool and stays there, held by value by one task (crates/db/src/txn/owner/). Its ID names the worker, so every request for it goes from the edge straight to that worker with Target::Worker, one hop in and one out, and the requests run one at a time, in arrival order, through the actor’s mailbox. There is no lock to take: the requests are messages.

The registry

The transaction registry (crates/db/src/txn/registry/) maps IDs to owners:

  • begin on a least-loaded worker, made explicit, wrapped as an OwnedTxn;
  • run: a request routed to the owning worker under a deadline; the actor lends the transaction to the statement and takes it back alone (Arc::try_unwrap; a still-borrowed transaction is TxnInUse, never waited on);
  • caller isolation: the request identity is the ownership key; a foreign caller gets NotFound, not someone else’s transaction;
  • idle sweeping: a deadline-queue job on each worker ends transactions idle past the timeout (default 600 s, swept every 60 s) - but only when the sweep message is next in the mailbox, so it can never interleave with a running statement.

Statement savepoints wrap every statement: a failed or cancelled statement rolls back to its savepoint, and the transaction stays usable for the next one. A statement’s conflict is returned to the caller (explicit transactions do not auto-re-run; the client is the retry policy). Only the creator can force_commit/force_discard; plain commit on an explicit handle is a typed error.

Commit fences

A subtlety with actors: the client may stop waiting (timeout, dropped connection) while the commit message is still in the mailbox. The commit still runs - the work was requested, and “the caller left” must not mean “the write vanishes” or, worse, “the write lands after a dependent read already reported it absent”. The CommitFence counts commits whose caller stopped waiting, and every new transaction waits while that count is above zero, so no new work starts until the abandoned commits have landed. The protocol has its own TLA+ model and a Lean proof of the counter swap (CommitFence.tla, crates/db/src/txn/fence.rs).

Auto-commit vs explicit

Every rule in this book applies to both; the differences are exactly three: explicit transactions own their retry policy (conflicts surface to the caller), span statements (savepoints, read-your-own-writes across requests), and live on one worker for their whole life (the actor). Auto-commit writes are the ones the engine re-runs (lifecycle).

Why an actor and not a lock. “One transaction, one statement at a time” is an ordering requirement, and a mailbox gives ordering without a lock object: requests queue in arrival order on the owning worker, the worker is never blocked (other documents’ work interleaves freely), the idle sweep is just another message, and there is no mutex to hold across an await, leak on panic, or convoy under load.

Reads

defradb.rs reads through one mechanism family, chosen by a single question: what does the decision depend on? The next chapter is the decision table, the diagram is the map.

Read scenarios

For every kind of read in defradb.rs, this page answers two questions: what (if anything) is validated at commit, and where does the value come from.

The decision table

Reads outside write transactions never conflict. A query, a status read, an arrival page: one consistent snapshot, never validated, never conflicting. Read-only transactions do not even begin an engine transaction; they pin a snapshot.

Inside one, the class of the key and the call decide the validation:

  • An Ordinary key (get, get_for_update): validated in full. An identical rewrite is not a change, so re-writing what you read does not conflict.
  • A projected read (get_parts(key, parts)): validated only against writes that touch those parts; in full if the read found nothing (absence is a decision about the whole value) or if the transaction then writes the key.
  • An unvalidated read (get_parts(key, &[])): never validated. Traversal hints, HNSW neighbours, head sets: reads whose result decides nothing that a later write of the key would invalidate.
  • A ContentAddressed key that was found: validated only for removal (the block you based a decision on must not have been collected).
  • A Log key (the arrival journal): never validated; a snapshot sees a dense prefix.
  • A scan inside a commutative prefix: the stretch is not recorded; writes inside it are blind.
  • A plain scan: yielded keys are not validated (phantoms do not matter to a snapshot read); a key the transaction then writes is validated as a read of that key.
  • ACP tuples and owner prefixes behind a write: validated point reads and scan_validated, so a revocation, grant or new owner committed first aborts the write.
  • A decision on what exists in a range (a claim queue): scan_validated; any newer write inside the range conflicts.

The same table, as code policy, lives in the repository’s working agreement, and the mechanisms are exercised end to end in crates/storage/src/backends/regolith/ and the collection read paths (crates/db/src/collection/crud.rs).

Where the value comes from

The engine’s read path serves a read with: the transaction’s own buffered puts, deletes and merges first, in operation order; then the memtables, then L0, then deeper levels by binary search. Zero copy, no lock.

A block-cache miss is the interesting case:

  • A get on the calling thread reads the device there.
  • A CacheOnly handle never touches the device: the miss becomes a WouldBlock carry an IoWait, the read is queued on this core’s own IoQueue, single-flight per block, the task awaits, and its own core’s poll completes it and resumes the task (the worker pool has the threading).

Why CacheOnly on workers. A blocking read on a data-path core would stall every task on that core behind one device latency. CacheOnly turns the miss into exactly the same suspension as any other await: the core runs other tasks, the completion arrives on the core’s own queue, and the task resumes where it left off. Single-flight per block means N tasks awaiting the same block cost one device read.

Writes

Every write operation decomposes into engine calls from one vocabulary: content-addressed puts that cannot conflict, blind merges that commute, ordinary puts and deletes that race when a decision needs one winner, and appends the engine orders. The next chapter is the full decomposition.

Write scenarios

Every defradb.rs write operation, decomposed into its engine calls. Blue keys never conflict; orange keys are races that need exactly one winner, surfaced as a typed Conflict.

Never conflicts

These writes commute, so concurrent writers never meet:

  • Blocks: a b-prefix ContentAddressed put of the block’s bytes keyed by its CID. Two writers of the same block write identical bytes: both commit.
  • Head sets: one blind merge of a set operand per document (add per published head, supersede per consumed parent).
  • Document values: blind merges of part operands (one operand per transaction holding its changed fields at their priorities).
  • Secondary index entries: blind puts and deletes.
  • The arrival journal: append with the document as its once key: the engine assigns the position in commit order and applies the once key exactly once.
  • Short IDs and policy IDs: Db::allocate, the engine’s atomic ID allocator.
  • Counters: blind merges with an exact partial_merge (wrapping i64 addition).
  • Block ownership: blind puts under /d/b/{cid}/{docID}.

One winner by design

These writes race on purpose, and the loser gets a Conflict with a reason:

  • Unique index keys: the second distinct value under a unique key loses.
  • The DocID mapping: exactly one creator materializes a document; the loser re-runs and applies its blocks as operands.
  • Deletion markers: delete racing delete or update produces the delete-after-delete no-op or the update-reports-not-found outcome.
  • Definition keys: DDL against its writers; a schema or index change races every writer that read the definition to decide.
  • ACP owner and tuples, inside the authorized transaction: registration is a validated scan of the owner prefix; revocation races the checks it invalidates.
  • The applied key per remote block: exactly-once application of a replicated block.
  • The same document parts written by two updates: the claim race; the loser re-runs and typically reports “not claimed”.

The operations, mapped

Where each operation’s writes live in the code:

  • Create a document (crates/db/src/write/autocommit/create.rs): blocks + CID, head-set merge, the whole stored document, index entries, the journal append (once key: the doc), the short-ID and DocID mappings, block ownership, and the ACP owner registration.
  • Update a document (crates/db/src/write/autocommit/update.rs): new field blocks, head-set operand (supersede old heads, add new), one document part operand, index deltas for intersecting indexes.
  • Delete a document (crates/db/src/write/autocommit/delete.rs): the deletion marker (ordinary key), index entry removals, a head operand, a delete block in the DAG.
  • P2P merge of remote blocks (crates/db/src/merge/pooled.rs): blocks, head sets, part operands, the applied key, the journal append, the DocID mapping.
  • Counter increment (crates/crdt/src/counter.rs): one blind merge; never a read-modify-write.
  • DDL: schema or index change: definition keys against current writers.
  • ACP: register an owner, add or remove a relationship: tuples in the same transaction the decision authorized.
  • ACP: create a policy: a Db::allocated policy id.

Why decompose writes this way. Each key’s conflict behaviour is chosen to be exactly as strict as the business question it answers. Unique constraints, existence decisions and authorization must have winners, so they are ordinary validated keys. Everything else commutes, so it is a merge, a content-addressed put, an append or an allocation: concurrent writers proceed in parallel, and the conflict rate of the workload, not the locking discipline of the database, is what it is.

Documents and CRDTs

A document in defradb.rs is two things at once: a local value (the materialized fields a query reads) and a DAG of blocks (the replicated, content-addressed history). Both exist for every document, and they answer different questions: the value answers “what is it now, here”; the DAG answers “how did it get here, and can others learn the same history”.

  • Blocks and the DAG: field blocks, composite blocks, signatures, encryption links, and the block builder.
  • CRDT types: LWW registers, counters, composites, and the priority algebra.

The document model

The DocID

A document’s identity is its DocID: a UUIDv5 over a fixed namespace of the genesis composite block’s CID (crates/document/src/doc_id.rs). The string form is {base32 version}-{uuid} (for example bae-...). The DocID is stable across replicas: any node that has the same genesis block computes the same DocID, which is what makes replication, dedup and the once-keys of the arrival journal possible.

The CID itself is not recoverable from the DocID string; it lives in the DAG.

Short IDs

Locally, every document also gets a compact short ID: a u64 allocated from /seq/doc in ranges of 1024 by a lock-free CAS allocator (crates/db/src/docid/map.rs). Short IDs key the datastore layout (doc_key(doc_short_id)), which makes iteration order match allocation order and keeps keys small. The systemstore holds the bidirectional mappings (short ID to DocID and back), plus the DocRef, and the block-CID-to-DocID ownership map that memory reclamation walks.

Allocation is Db::allocate: engine-side, atomic, and safe to call inside a retried closure because a reserved range survives attempts (an attempt never allocates twice; the prepared-inputs rule from the doctrine chapter).

The stored format: documents as parts

The materialized value of a document is a StoredDocument (crates/document/src/stored.rs): magic DFV\x01, then fields keyed by stable per-version u32 field IDs (not names: renames must not rewrite every document), each with a kind (Lww, Int64, Float32, Float64), a priority, and bytes (CBOR for LWW values, big-endian numbers for counters). An LWW field with empty bytes is a tombstone, and the priority survives materialization: a delete is an LWW write that wins by priority, not a special row.

The whole document is one value under one key, and the field IDs are the document’s parts: this is what makes projected reads (get_parts(key, parts)) and blind part-operand merges the read and write primitives of the document. Part IDs are allocated from the systemstore and persisted per schema version (crates/db/src/collection/parts.rs), so two writers on two replicas name the same fields with the same part IDs.

The in-memory document

The Document in memory (crates/document/src/document.rs) carries the schema-typed field map, the current head CID, dirty tracking, the collection reference, counter deltas for updates, and the write preparation (precomputed keys and identity). Documents are built from client JSON against the collection’s schema, validated, and then either computed into blocks (create/update) or read back from the stored format.

Deletion

Deletion is logical: a deletion marker under d/del/ (an Ordinary key, so racing deletes have a winner), the index entries removed, the series released, and a delete block appended to the DAG (status DELETED). The blocks and value history remain until a retention policy prunes them (see Memory reclamation), so a delete replicates like any other write and time travel still sees the document’s life.

Why UUIDv5 of the genesis CID, and why short IDs at all. The DocID gives a replica-stable identity derived from content (no coordinator, no counter, no allocation race across nodes). The short ID gives a compact, locally ordered key. Two identities, two jobs: one travels the network, one stays in the keys.

Blocks and the DAG

Every write to a document produces blocks: content-addressed CBOR payloads whose links form a Merkle DAG per document. Blocks are the replication unit: P2P ships blocks, merges apply blocks, history queries walk blocks, signatures sign blocks.

What a write produces

The block builder (crates/db/src/block/builder/) computes, for one write:

  • Field blocks: one per modified field, carrying the CRDT delta (an LWW value with its priority, or a counter increment) and linking the field’s previous heads.
  • Encryption blocks: when a field is encrypted, a separate Encryption block holds the fresh AES-256 key, and the field block links it. The block CID is computed over the ciphertext. With a KMS configured, the key is released through it (gated by its policy); without one, the node reads the key from the Encryption block it stores and decrypts locally, so field confidentiality against the operator exists only with a KMS in the path.
  • Signature blocks: when signing is configured, a signature over the block (or a batch signature: a Merkle root over a set of CIDs, signed once per commit).
  • Immutable blocks: fields marked @immutable are frozen as plaintext blocks at creation.
  • The composite block: links all field blocks of this write, carries the document status (active/deleted), and links the previous composite heads as parents. The composite block’s CID at create time is the document’s genesis, hence its DocID.
  • Collection blocks: for branchable collections, a collection-level delta linking the document’s composite block, blind-merged into the collection head set.

CIDs

A CID is computed from the block’s canonical bytes (crates/defra-core/src/block.rs). Identical bytes produce identical CIDs: that is why two replicas that apply the same writes produce the same history, and why block writes are ContentAddressed and cannot conflict.

Priorities

Every CRDT delta carries a priority (a u64 varint, crates/crdt/src/priority.rs): create writes priority 1; an update writes the field’s current max priority plus one; the composite writes the document’s max plus one. Priorities are what order concurrent LWW writes deterministically without a coordinator: given two values, the higher priority wins, and the merge algebra is proven convergent in Lean.

Verification

Replicated blocks are checked before merge (crates/db/src/block/verify.rs): the CID must match the bytes (content integrity), and attached signatures are verified when present (including BLS-augmented batch signatures); unsigned blocks are supported. The read gate checks ACP before a block is even served. A document’s DAG that fails verification is quarantined (the PendingDagQuarantined event carries the forensics).

Reading the DAG back

History reads walk the DAG: _commits by CID or depth (crates/db/src/read/commits/), versioned (time-travel) reads walk from a target CID back to genesis and replay CRDT deltas forward (crates/db/src/read/versioned.rs). The query chapter covers the API surface.

Why blocks when there is a local value. The local value is an index of “now”; the DAG is the truth. Replication, verification, encryption scoping, signing, history and GC-retention all operate on blocks, and any replica can rebuild any document’s value from them. The materialized value exists so queries never walk a DAG to answer “what is this field”.

CRDT types

Conflict-free replicated data types are the reason replication needs no coordinator: nodes that have received the same set of deltas converge to the same state whatever order they applied them in, and that convergence is a theorem, not a hope. (Nodes with different subsets are simply behind; floating-point counters are the documented exception and are covered below.) defradb.rs uses four.

LWW register

The workhorse. A field value with a priority: given two writes, the higher priority wins; equal priorities break ties deterministically on the value bytes (crates/crdt/src/lww.rs). Empty data is a tombstone whose priority still counts, so a delete beats a lower-priority write and loses to a higher one. Every ordinary field is an LWW register by default.

Why the byte tie-break. Two replicas resolving the same two equal-priority writes must pick the same winner without communicating. A total order on (priority, bytes) gives them one, and the convergence proofs lean on it.

Counter

A single accumulated value with blind-merge increments (crates/crdt/src/counter.rs). This is deliberately not a classic PN-counter with two registers: an increment is a document-part operand (kind INT64/FLOAT32/FLOAT64), and i64 addition is wrapping and order-independent (proven in Lean), so any grouping of increments folds to the same sum. Idempotence of replicated application is enforced one level up: the applied key of a remote block means the same increment block is never applied twice. A nonce keeps each increment block’s CID unique.

Floats are documented as non-convergent under addition reordering (IEEE addition is not associative); the engine keeps application deterministic by sequence order, and the honest caveat is written beside the code.

Composite

The document-level delta: which field blocks this write produced, the document status (active/deleted), and its priority. The composite is what links a write into the DAG; its priority is the document max plus one.

Head sets (the DAG CRDT)

Which heads a document (or collection) currently has, as one value under one key, updated by blind merges of set-operand state functions. The mechanism gets its own chapter because it is also the cleanest example of the state-function pattern.

The algebra, and where it is proven

The merge laws these types must satisfy (commutativity, associativity, idempotence, order-independence) are proven in Lean in proofs/lean/ (CRDT merge laws, convergence family), and the temporal half (every node eventually receives every delta under eventual connectivity) is a TLA+ model. Convergence is the product of the two: neither half alone is the theorem. See Verification.

Why CRDTs instead of operational transforms or last-write-wins timestamps. Wall clocks do not order events across nodes, and OT needs a serialization point. CRDT merges are associative, commutative and idempotent, which means the transport can redeliver, reorder and partially deliver, and the state still converges. The costs are explicit: tombstones must survive long enough (priorities carry them), and metadata (heads, priorities) has to be maintained, which is what head sets and the priority index do.

Head sets

A document’s heads are the frontier of its DAG: the composite and field block CIDs that no later block supersedes. Merge needs them (a replicated write applies against the heads it finds), history queries need them (walk from the heads), publication needs them (a new block supersedes its parents). defradb.rs tracks heads in a head set: one value under one key per document, updated by blind merges.

The layout

Document head sets live under h/hd/, collection head sets under h/hc/ (crates/db/src/block/heads.rs). A set value holds, per name, one of three states: Absent, Ahead (a child arrived before its parent), or Live(priority). Names are {field}/{cid} pairs, so one set holds every field’s heads plus the composite C heads.

The operands

A publication merges one operand that says, per name, what to do in every state it may find (the table is in the merge operator chapter): add(p) records a new head (and consumes an Ahead marker waiting for it), supersede removes a parent the write consumed, supersede_ahead records a parent that has not arrived yet. Writers never read the set to decide: one operand per set per transaction, merged blind, so concurrent publications never conflict.

Why each name is a part

Each name’s rapidhash is a part ID. A publication that read the heads it supersedes (deciding, say, “these are the parents of my new block”) did a projected read of those names’ parts, so it conflicts only with operands that touch those names: a concurrent publication of a different field does not disturb it.

The priority index

Beside the set, each publication writes an entry under h/p/{doc}/{priority}/{cid}: the commit priority index that history queries use to walk a document’s DAG by height without scanning blocks. Entries are ordinary keys; pruning history deletes them (see Memory reclamation).

Collection head sets

Branchable collections keep a collection-level head set (h/hc/), blind-merged the same way, so a collection’s published block set is itself a CRDT: replicas converge on the same set of collection blocks without coordination.

Why sets instead of per-head keys. The pre-regolith layout kept one key per head and read before writing: every publication was a read-modify-write over a growing key range, serialized by a lock, and a replicated parent arriving late was a special case. The set encoding makes the whole update one commutative merge, makes “parent not here yet” a first-class state (Ahead) instead of an error, and lets two writers publish concurrently because their operands compose. It is the same trick as counter increments, lifted from numbers to a small state machine.

The arrival journal

The arrival journal answers a deceptively hard question: in what order did documents first appear on this node? Clients that consume events (a search indexer, a projection builder, an agent) need a durable, gap-free feed of arrivals, and ordinary key layout cannot give it: documents arrive from local writes and P2P merges on different cores, and “sorted by DocID” is not an arrival order.

The mechanism

Each collection has a journal, stored as a Log under s/arrival/ (crates/db/src/event/arrivals.rs):

  • /arrival/{collection}/head: the number of rows,
  • /arrival/{collection}/row/{cursor:020}: one row per position, holding a DocID,
  • /arrival/{collection}/doc/{doc}: the once key, the document’s cursor.

A create (local or replicated) appends to the journal inside its own transaction, with the document as the once key. The engine assigns positions in commit order: nothing conflicts, and a document appended twice (a local create racing a P2P merge of the same document) keeps exactly one row, because the once key is applied exactly once. Position keys are zero-padded to a fixed width ({cursor:020}, crates/storage/src/backends/ [regolith](https://sourcenetwork.github.io/regolith/)/log_layout.rs) so they sort in position order; the layout is frozen: a store keeps reading its journal across releases.

The dense prefix

A reader at a snapshot sees a dense prefix: rows 1..head, no gaps. A later arrival commits at a position above head (positions are assigned in commit order and become visible in sequence order), so a reader that stored its cursor at 43 will see row 44 next, never a hole at 44 filled in later. The read path enforces it as an invariant, not a hope: a missing row inside the read range is a hard error (“missing arrival row”), never silently skipped.

The API: _documentArrivals

The GraphQL system collection exposes the journal:

{
  _documentArrivals(collection: "Users", after: 42, limit: 100) {
    head
    next
    entries { cursor docID }
  }
}

At the GraphQL surface an omitted limit defaults to 256, and a limit of zero or above 1024 is rejected (as is a docID list longer than 1024); the lower-level database read clamps its page to the 1024 ceiling. The result carries head, the next cursor, and ACP-filtered entries (each entry’s document is checked before it is returned). The client consumes a page, processes it, stores its cursor durably, and continues: the same discipline as a CDC log, minus a server-side session.

Why a log the engine assigns instead of a table the database numbers. Two writers on two cores cannot number rows without a serialization point. The engine’s commit-ordered append is the serialization point, but it costs nothing extra: the position is assigned in the same ordered step of the commit that makes the document visible, so the journal order and the visibility order are the same order, by construction. The once key gives exactly-one-row-per-document without a unique index, and the dense prefix falls out of positions being visible in sequence order.

Querying

defradb.rs is queried in GraphQL. The pipeline from a GraphQL string to results is classical (parse, plan, execute), and the interesting parts are where defradb.rs’s storage decisions show up: index selection against part layouts, permission filters as plan nodes, and history queries that walk the DAG.

  • The GraphQL pipeline: parse, map, plan, execute; ACP placement; pooled execution.
  • Indexes: secondary, unique, full-text and vector indexes, and how they are maintained.
  • History: _commits and time travel: commit queries and versioned reads.

The GraphQL pipeline

The pipeline, in one line (crates/query/src/lib.rs):

GraphQL string -> Parser -> Mapper -> Planner -> Plan nodes -> Executor -> Results

Parse and map

The parser (query_parse/) is built on graphql_parser. It produces a typed ParsedOperation: queries (with selects, filters, ordering, aggregates, cursors, limits), mutations (create/update/upsert/delete on collections, or raw documents), subscriptions, and introspection. System collections are parsed here too: _commits (with depth, cid, height ranges) and _documentArrivals (with after, limit, docID). Depth, width and filter complexity are bounded by explicit limits, because a query is untrusted input at a trust boundary.

Schema SDL is parsed in the same crate (sdl_parse/), and the GraphQL schema a client introspects is generated from collection definitions (schema_gen/).

Prepare

Mutation preparation (crates/query/src/runner/prepare.rs) runs once per request, outside any transaction retry: write preparation resolves KMS keys, embeddings and signatures; batches group; ACP-transactional providers bind. Remote inputs are resolved in waves at the edge: an input that is not yet local ends the wave (NeedsInput), is fetched, and the request re-prepares with it memoized by request bytes. This is the doctrine’s “everything with an outside effect is prepared” made concrete.

Plan

The planner (planner/) turns the mapped operation into a tree of plan nodes, in the Go-compatible order (joins below selects):

  • Scan and index selection: filters are matched against available indexes (filter_to_scan, cost estimates, scan types: exact, range, prefix, IN, OR). Vector similarity routing picks a vector engine when the filter shape allows.
  • Joins: relation joins (one/many), secondary-id joins, aggregate joins.
  • Aggregates, group-by, order-by, limit; cursors applied by walking the tree to the scan nodes, so pagination stays index-ordered.
  • Views: materialized views read a cached node; live views plan the underlying query.
  • Permission filters: when a collection has a policy, the planner wraps its plan in a PermissionFilterNode that checks each document’s access (bounded, with a small in-flight cap). App read validators hook the same node.

Execute

The executor (crates/query/src/runner/executor.rs) is a Volcano-style iterator over the plan: each node pulls from its children. Reads stream: a scan yields pages from the storage iterator, never a materialized set. Execution happens on a pool worker, routed at the edge; when the request names an explicit transaction, it goes to that transaction’s owning worker (see Explicit transactions).

ACP runs in two places, both inside the request’s snapshot:

  • Node access control (NAC) before execution: a denial yields an empty result (Go parity), not an error, for queries.
  • Document access control (DAC) as the permission filter node per document, and for mutations as pre-filtered visible doc IDs. _commits and arrivals entries are filtered the same way.

Deadlines ride the request end to end; a slow query fails its deadline rather than running unbounded.

Why Volcano iterators and why planning joins below selects. Streaming execution keeps memory flat in the result size (a page in flight, never the set), and pull-based iterators let limit/order/cursor pushdowns do their work before a row ever reaches the surface. The join placement is Go compatibility: plans match the reference implementation so explain outputs and optimizations correspond.

Indexes

Indexes are maintained inline in the write path: every document write updates exactly the indexes whose fields it touched. Four kinds exist (crates/db/src/index/, crates/storage/src/index/):

Secondary (ordered)

A sorted mapping from field value to DocID, blind puts and deletes, kept per index (IndexDataStoreKey under the d/ family). Multiple fields, arrays (multiple value sets per document) and partial indexes (filtered) are supported. The planner uses them for exact, range, prefix, IN and OR scans.

Unique

The same layout with a uniqueness decision: the entry key is an Ordinary key, so a second distinct document under the same value loses the commit and the client sees a typed conflict. Two subtleties are deliberate:

  • Self-healing: a local write that finds a stale unique entry whose holder no longer exists overwrites it (the entry was garbage, not a constraint violation).
  • Merge-path resolution: two replicas concurrently creating the same unique value both persist (CRDT merges cannot roll back), and the index resolves deterministically: the lexicographically smallest public DocID wins the entry, both documents exist, and a UniqueIndexConflict event tells the operator. Local writes stay strict; only replicated concurrency resolves this way.

Full-text

Tokenized, language-aware inverted indexes with BM25 scoring (crates/storage/src/index/fulltext.rs), synthesized from @fulltext schema directives under internal names (__fulltext__:{field}). Corpus statistics (document counts, field lengths) are maintained as blind STATS merges (checked i128 deltas), so concurrent indexers commute. Query time scores with BM25 over the stored statistics.

Vector

Four engines behind one interface (crates/db/src/index/vector/engine/): flat (exact brute force), HNSW (the Malkov-Yashunin graph; deterministic level seeds; links maintained by blind VECTOR_LINKS merges), IVF (inverted lists with product quantization) and SSG (Satellite System Graph), plus DiskANN-style PQ-coded resident graphs sharing code caches on the DB. Structural rules live in the merge operator: a blind addition can never raise a node’s height or add a self-link, so graph maintenance never needs locks. Similarity queries route through the planner to the engine (crates/query/src/plan/similarity.rs); HNSW advisory reads during maintenance are unvalidated part reads, so building never conflicts with querying.

Lifecycle

Indexes are created with a bulk backfill (resumable at open, crates/db/src/index/ backfill.rs), rebuilt on demand, and re-created when a schema change requires it (owed reindexes settle at startup). Deletes remove entries page by page; the unique conflict event and index reconciliation have TLA+ models (see Verification).

Why inline maintenance instead of background catch-up. An index that lags its collection returns wrong answers to queries that trust it. Inline maintenance makes index state part of the same transaction as the document write: either both land or neither does, and a query’s snapshot sees a document and its index entries together. The cost (index writes in the commit) is why on_document_update_modified updates only the indexes whose fields the patch intersects.

History & Time Travel

Because every write is a block in a DAG, history is queryable first-class.

_commits

The _commits system collection exposes the block DAG (crates/query/src/runner/commits.rs, crates/db/src/read/commits/):

  • by CID: one block, or a traversal to a depth following block heads;
  • from heads: the frontier of a document (or collection), depth-limited;
  • by height range: the commit priority index (h/p/) turns “commits of this document between these priorities” into an index scan, no DAG walk.

Blocks are decoded into commit documents (field deltas, links, priorities) and returned in the Go-compatible order. Every result row is ACP-checked: a commit reveals a document’s data, so commit queries are filtered exactly like document queries (this is the “gate commit queries with DAC” behaviour, ported from Go).

Time travel (versioned reads)

A versioned read reconstructs a document as of a target CID (crates/db/src/read/versioned.rs): walk the DAG from the target back to genesis, replay the CRDT deltas forward, and return the state. Encrypted fields resolve their DEKs through the KMS during the replay (prepared inputs, never a remote call per field). Versioned reads are also how “the document at this commit” is served to clients that pin versions, and how collection-level CIDs work for branchable collections (the collection block resolves to a set of document composites).

Deleted documents remain visible through indexed historical queries until retention prunes the history: deletion is a block, not a shredding, and the queries honour that.

Downsampling and retention (the consumer side)

Downsample plans periodically roll source documents into downsampled targets (summaries per window); retention policies then prune source history (Memory reclamation covers the write side). Versioned reads are what makes “prune old source history” safe: the downsample target holds what queries need, the source’s old heights are gone, and history queries that target a pruned height fail cleanly rather than lying.

Why replay instead of snapshots-per-version. Storing every version materialized multiplies write amplification by the number of queried versions. The DAG already holds each delta exactly once; replay is a read-side cost paid only by history queries, bounded by the walk, and the priority index keeps the common cases (head, range of heights) off the walk entirely.

Access Control

defradb.rs has two authorization scopes, both built on one engine:

  • DAC (document access control): per-document policy, registered by the document’s owner at create time, evaluated on every read and write of that document.
  • NAC (node access control): one policy over the node itself, gating administrative and management operations.

Local ACP evaluates inside the request’s transaction, on the same snapshot as the data; Vera decisions happen at the edge, with their staleness documented. The chapters:

  • The Zanzibar engine: policies, relations, tuple-to-userset evaluation, the goal-tree checker.
  • DAC and NAC: the document and node scopes, registration, the bypass privilege.
  • ACP inside the transaction: how decisions are validated, why no public window exists, and revocation.
  • Vera: external, chain-verified policy decisions.

The Zanzibar engine

crates/zanzibar is a standalone implementation of Google’s Zanzibar permission model, and crates/acp builds DefraDB’s access control on it. No global mediator, no special cases in the query engine: authorization is evaluation of a policy over relationship tuples.

The model

Three nouns:

  • Policies (Policy, Resource, Relation, Subject): a policy names resource types, relations on them, and permission expressions over those relations. DefraDB’s DPI format is a small YAML dialect (crates/acp/src/policy_yaml/); the default document policy (used when a collection carries no explicit one) has an owner relation, an admin computed from owner, direct reader/updater/deleter relations, and read/update/delete permissions computed as unions over owner, admin and the direct relations.
  • Relationship tuples: (resource, relation, subject) facts, stored under a/zanzibar/ as Ordinary keys. Subjects can be actors, wildcards, or usersets (a subject that is itself a relation on another object).
  • Relation expressions: the algebra evaluated to answer “may this identity perform this permission on this resource” (crates/zanzibar/src/expression/): This (a direct tuple), ComputedUserset (follow to another relation on the same resource), TupleToUserset (follow a tuple relation to a target, then evaluate a computed relation there), and the set operations Union, Intersection, Difference.

Evaluation

The checker is a goal-tree search with cycle detection (crates/zanzibar/src/engine/evaluate.rs):

  • Union short-circuits on true; Intersection short-circuits on false;
  • Difference requires the base to be proven true and the subtraction proven false; a cycle-truncated subtraction branch is indeterminate, and indeterminate fails closed (Error::IndeterminateExclusion), never silently grants;
  • every check runs under explicit work limits (depth and step budgets) and a per-check memo cache with a charged budget, so a malicious policy cannot make evaluation unbounded;
  • batch checks share one cache (check_many).

Policies are immutable once stored; the node keeps them in a lock-free policy snapshot (an Atom-swapped lookup table, crates/acp/src/policy_cache.rs) that reads never lock to consult.

Policy identity

Policy IDs come from the engine’s Db::allocate (the same atomic allocator as short IDs), so two replicas allocate distinct policies without coordination, and a policy body is content-checked: a different body under an existing ID is a typed error, not a silent overwrite.

Why Zanzibar, and why fail-closed on indeterminate. Relationship tuples express sharing graphs (owner grants editor on a doc to a group object) that boolean flags and ACL rows cannot, and the evaluation model is well-studied. The fail-closed rule is honesty applied to permissions: when the engine cannot prove absence (a cycle cut the search), it reports indeterminate, and indeterminate denies. A permission system that guesses is a vulnerability with good manners.

DAC and NAC

DAC: document access control

The DocumentACP trait (crates/acp/src/dac.rs) is the document-scope interface: register a document’s owner, check access, add and remove relationships. Implementations:

  • Zanzibar-backed local ACP (the default): tuples in the local store, evaluated by the engine above.
  • External ACP (Vera): decisions from an external chain, wrapped so the database still gates every read (next chapter).
  • An in-memory variant for tests.

The contract every implementation honours:

  • Registration at create: the document’s owner relationship is written in the create transaction. Between the document’s rows and its owner tuple there is no commit boundary, hence no window where the document exists but is public.
  • Unregistration at delete, in the delete transaction.
  • Exactly one owner: registering a document that has one fails with DocumentAlreadyRegistered; the owner relation itself can neither be added nor removed by sharing.
  • Read checks are unions: read is answered by any permission that implies read, matching the Go implementation’s ImplyDocumentReadPerm.

Sharing is add_relationship (grant), revocation is delete_relationship; the requestor must hold the relation’s managing permission. DAC decisions run per document inside the query’s permission filter node, per mutation, per _commits row, and per arrival entry: anything that reveals a document’s data goes through the same check.

NAC: node access control

NAC is one policy over a single singleton object (the node), always local (no Vera option), with a lifecycle: not configured -> enabled -> (optionally) temporarily disabled -> purged. It gates administrative surface: collection and index management, backup, P2P configuration, lens, views, and every management HTTP route (the route permission map lives in crates/http/src/route_permissions.rs. Some 51 node permissions exist, all admin-only (owner + admin).

Two properties worth knowing:

  • While temporarily disabled, all writes are blocked (including admin changes): a disabled NAC that still accepted admin writes would let an attacker re-enable it with themselves as admin.
  • bypass-dac: a privilege on the NAC object that lets an authenticated identity skip per-document DAC checks (service accounts, indexers). It is checked first on every read path, and it exists only when NAC is enabled.

Where identities come from

Callers identify with decentralized identities (DID-key over Ed25519, secp256k1 or secp256r1 keys; crates/identity), presented as JWT bearer tokens (Go-jwx-compatible JOSE, with bounded clock skew). Anonymous requests map to the wildcard subject: whatever the policy grants *. Identity travels on the request context, never in a thread-local.

Why two scopes. The questions are different: “who may read this document” is data (it belongs with the document, replicates with it, and is answered by its owner’s policy), while “who may reconfigure this node” is infrastructure (it does not replicate, and it must keep working when documents are being replicated in). Splitting them keeps each policy small, each check local, and neither a choke point for the other.

ACP inside the transaction

The rule that makes local ACP trustworthy: every access decision runs in the transaction it authorizes, on the same snapshot as the data it gates. Not a pre-check, not a cache consultation before the transaction: inside it, validated exactly like a data decision. An external provider (Vera) cannot join a local transaction; its shape is the exception below.

The create path: no public window

A create writes the document (blocks, value, index entries, journal append) and then, in the same transaction, scans the document’s owner prefix with a validated scan and puts the owner tuple. The commit that makes the document visible also makes its owner tuple visible: there is no commit boundary between them, hence no window where the document exists unowned and public.

A concurrent upsert/create of the same document by another identity loses that race: its validated scan of the owner prefix meets the first writer’s tuple put (mine ScannedRange, theirs Put), its re-run finds the existing owner, and business logic answers AlreadyRegistered (or a no-op when the owner is identical).

The read path: one snapshot

A read-only query decides DAC at its own snapshot: the tuples and the document rows come from the same consistent view. There is no “authorization checked, then data read” pair of snapshots to disagree.

The write path: validated tuples

A write’s authorization is a decision on tuples, so it uses exactly the read rules for decisions:

  • point reads of the tuples that grant the identity’s permission are validated reads;
  • decisions over a set (the owner prefix, a claim queue) are validated scans.

A revocation, grant or new registration that commits first aborts the decision, the attempt re-runs, and the re-run decides again on the fresh tuples. The revocation race (the race gallery covers it step by step) lands as: the write never commits after the revocation it raced.

External providers (Vera) under the same shape

An external decider cannot join a local transaction. The database keeps the shape anyway: the create writes an owed registration record (a pending marker under the ACP namespace) in its own transaction; until the provider confirms, the document’s reads are gated to its creator alone; a paged redrive settles owed registrations; and during engine retries, an external decision is asked once, memoized by request bytes, and replayed identically for later attempts. Failures of the provider fail closed (Unavailable denies).

The query engine’s side

The planner wraps collection plans in permission filter nodes; _commits rows, mutation target sets and arrival entries are filtered through the same checker; the block read gate checks ACP before serving replicated blocks. Unregistered documents are public only when the node’s configuration says so.

Why validated, not cached. A cached authorization is an answer about the past being reused for the present: between cache fill and use, a revocation may have landed, and the write would commit on an authorization that no longer exists. Validated tuples make the authorization itself part of the commit’s consistency guarantee: if anything it rested on changed, the commit loses, exactly like a data race. That symmetry is the entire trick, and the TLA+ models for ACP soundness and the deferred-ACP overlay pin it.

Vera: external policy decisions

Vera moves authorization off-node: an external chain (CometBFT or a native commonware-based chain) holds the policies and tuples, evaluates checks, and proofs flow back to the database.

What it is

crates/vera defines the VeraProvider interface: create policies, register and archive objects, set and delete relationships, check access. Two implementations:

  • CosmosProvider: a Cosmos-SDK chain over LCD/gRPC, transactions broadcast to it, and a WebSocket subscriber for cache invalidation.
  • VeraRsProvider: the native vera.rs chain (commonware consensus), commands signed and submitted through a worker, and the chain state verified by a light client (trusted consensus key, height tracking).

Both are wrapped as a DocumentACP and installed as the node’s document ACP. Because the provider cannot join local transactions, the node wraps it in the external-ACP adapter: owed registrations, gated reads until confirmation, fail-closed Unavailable (the previous chapter’s shape).

Why it exists

Some deployments need authorization decisions that no single database node can make or forge: multi-party deployments where the policy is shared infrastructure, audits that require the decision trail to be external to the data holder, or thresholds the chain provides. Vera is opt-in: without it, local Zanzibar ACP is the whole story.

The performance shape

External decisions are remote inputs, so they follow the doctrine’s remote-input rules: resolved at the edge, never inside a retried closure, memoized by request bytes across attempts, single-flight, batched, cached (access-decision and policy caches with the circuit breaker and tuning knobs in crates/vera/src/), with staleness documented and a persisted-decision path for signers to verify via the light client.

Why fail closed. An external decider that times out is not “probably fine”: it is a decision the system cannot make. Granting on timeout converts an outage into an escalation; denying converts it into a latency event. The interface says so in its error type: Unavailable means all decisions fail closed.

Threading

defradb.rs’s execution architecture is thread-per-core: one pinned worker per CPU core, each running its own executor, with the network on a single separate runtime. This part explains why that architecture was chosen and how each piece works.

  • Why thread-per-core: the reasoning, and what it buys.
  • The worker pool: workers, inboxes, routing, document affinity, I/O queues.
  • The network edge: the one tokio runtime and what lives on it.
  • One thread: wasm and single-core: the same code on one thread.

Why thread-per-core

The threading model is not a style preference; it is the shape the rest of the design pushes you towards. Three pressures, one conclusion.

Pressure one: the engine completes I/O on the asking thread

regolith’s non-blocking API is built on per-thread IoQueues: a CacheOnly read miss or a pending commit ticket becomes a unit on the caller’s own queue, and the completion arrives on that same queue. That design exists to make I/O wait-free for everyone else: a busy core is never woken to service someone else’s completion, and no core ever waits on a lock held by a thread that is blocked on the device.

But it only works if the task that awaits is still on that thread when the completion arrives. A work-stealing executor that migrates the task to another core between the await and the wakeup breaks the invariant: the completion lands on a queue whose owner is not waiting for it, and the task is on a queue that will never see it. So the executor must be local, and tasks must not migrate.

Pressure two: shared mutable state is the tax on cores

Every cache line a second core touches is coherence traffic; every mutex a second contender takes is a cross-core round trip that can park both. The database’s hot state (per-collection indexes, buffered iterators, transaction objects, CRDT accumulators) is vastly cheaper if one core owns it and it never leaves L2. defradb.rs leans into that: a worker’s state lives on the worker; read-mostly state (schema definitions, the ACP policy snapshot) is an immutable snapshot published atomically and copied per worker; anything that must cross threads crosses as a message, never as shared memory.

Pressure three: the workload has natural affinity

A single document’s writes and merges must be ordered somewhere: regolith validates every commit wherever it runs, but one-at-a-time-per-document is what makes conflicts rare (the race gallery exists between racing decisions, not inside one document’s stream). Document affinity (hash the collection and DocID to a worker) gives that ordering for free, with no lock, as long as the router is stable and requests actually go there. That requires routing at the edge, once, and no hopping.

What it buys

  • No task stealing: wakeups never cross cores; caches stay warm; tail latency stops being a scheduling lottery.
  • No locks on the data path: ownership replaces locking. Where two tasks must coordinate, they are on the same core, or they go through a lock-free queue.
  • Throughput that scales with cores: each core runs its full pipeline (parse to commit) independently; the only shared points are the engine’s own lock-free structures and the commit pipeline’s helping protocol.
  • One code path: the same executor, the same queue discipline, on one core (wasm, embedded) or sixty-four. Nothing requires a second thread.

The discipline it demands

Thread-per-core is a contract, not a feature: nothing on a worker may block the thread (no block_on, no thread::sleep, no spin-wait); long tasks yield after a bounded slice so the core stays fair; every wait is an .await on something the worker’s own core completes; futures on the data path need not be Send, and that liberty is used. The repository’s lints and review rules enforce it; the pool chapter shows the machinery.

Why not just tokio everywhere. tokio is an excellent network runtime, and defradb.rs keeps exactly one for that job. But a general-purpose stealing runtime is the wrong shape for a storage engine’s data path: it migrates tasks (breaking queue affinity), its locks are designed for coarse sharing, and its “just spawn more tasks” answer to blocking work is precisely what a per-core design exists to avoid. The split is not tokio-versus-not; it is one runtime per job: a network runtime for network-shaped work, pinned cores for database-shaped work.

The worker pool

The pool (crates/workers) is the compute side of defradb.rs: one pinned worker per core, each with its own local executor.

Workers

Each worker is a pinned thread (the pool’s placement spreads workers across NUMA nodes and L3 domains; spare cores become the background set for the edge, compaction and blocking threads) running a round:

  1. drain its inbox in batches,
  2. poll ready tasks (under catch_unwind, with heartbeats),
  3. poll its hook, which is the regolith IoQueue machinery,
  4. fire timers from its deadline queue (periodic jobs, the idle sweep).

Tasks are spawned with spawn_local and never migrate: a waker from any thread puts the task back on its worker’s run queue. Data-path futures need not be Send.

Routing at the edge

The target is chosen once, at the edge (crates/workers/src/pool/routing.rs):

  • Target::Worker(n): an explicit transaction’s owner. A transaction is begun on a worker and stays there for its whole life; its ID names the worker, so every request for it goes straight to that worker, one hop in, one out.
  • Target::Key(hash): document affinity. The hash picks one worker, which runs one keyed task per key at a time, the rest waiting in arrival order, so two keyed tasks on that worker never interleave at an await. The guarantee is per worker, not absolute: GraphQL and REST hash the collection by its name while a P2P merge hashes it by its ID, so a local write and a merge of one document may run on different workers, and while a home worker is stuck its keyed jobs move to a fallback on the same node. Correctness never depends on the affinity; the engine validates every commit wherever it runs. The GraphQL router sends a mutation naming exactly one document here (crates/query/src/pooled/route.rs); P2P merges use the same affinity (crates/db/src/merge/pooled.rs).
  • Target::LeastLoaded: everything else (read-only queries, batch work), a power-of-two choice among the caller’s node.

No request hops worker to worker. Correctness never depends on placement: regolith validates every commit wherever it runs. Affinity is a performance and contention property, not a safety one.

Inboxes

Each worker has a bounded inbox (bounded by items and bytes); cross-thread submission is batched so a batch crosses to each worker once. A monitor detects stuck workers and moves movable queued jobs. Blocking work (and pinned off-worker code) goes to separate background/blocking pools, never onto a data-path worker.

The I/O queues

Each worker holds one regolith IoQueue per database, opened lazily on its own thread the first time a transaction reaches that database (crates/storage/src/backends/regolith/worker_io/). A transaction on a worker reads CacheOnly on that queue (a miss suspends the task on an IoWait, never the thread on the device) and commits with commit_nowait, whose ticket the same queue completes.

Between tasks, the worker polls its queues with a budget: completions run regolith callbacks (which may re-enter), progress folds into the round, and when the worker runs out of ready work it hands its waker to every queue and parks. A busy core is never woken; a resting one is woken by the first completion. Single-flight per block means one device read serves every waiter for that block.

Callers off the pool (tests, one-shot tools) still get correct behaviour: the store borrows an idle queue, drives its own polling inline in the calling task (crates/storage/src/backends/regolith/worker_io/drive.rs: poll the future; if pending, poll the queue; completions loop, otherwise park the task on the queue’s idle waker), or falls back to blocking reads and a synchronous commit. Off-pool calls are counted (off_pool_calls) so a request that was not routed is visible in telemetry.

Remote inputs

KMS keys, signatures, Vera decisions and embeddings are resolved before the transaction, at the edge: single-flight per request key, batched, cached, deadlined, bounded. A P2P merge is admitted only once its blocks and keys are local. This is why workers never block on the network: by the time work reaches them, nothing remote is missing.

Why keyed tasks, not keyed locks. The obvious design is a per-document mutex; the pool’s is a per-key FIFO inside the executor. Same ordering guarantee, but the waiting “holders” are queued tasks, not parked threads: the core keeps running other documents’ work while one document’s turn passes, and no lock object exists to be held across an await by mistake.

The network edge

Every network-facing component runs on one tokio runtime, held in one place: the Edge (crates/edge). Natively it is a single runtime; in the browser it is the event loop behind the same handle. Every network component (the HTTP server, P2P, the KMS transport, the Orbis and Vera clients, the embeddings fetcher, telemetry export) is handed an Edge at construction. Nothing finds a runtime ambiently: no Handle::current, no second runtime, ever.

What lives there

  • HTTP: the axum server; whole data-path routes move onto the pool through an OnPool layer, document-named paths to the document’s worker (crates/http/src/pool_layer.rs); transaction routes, SSE and subscriptions stay on the edge (they are streams, not database work).
  • P2P: the iroh endpoint task (all protocols muxed over one ALPN), or the libp2p swarm where that transport is used.
  • Remote input services: the KMS pubsub transport, Vera clients, the embeddings client: single-flight, batching, byte-bounded caches.
  • pg-compat (the Postgres wire server) and telemetry export.

What deliberately does not

The data-path crates (storage, datastore, blockstore, crdt, defra-core, query, db, acp, zanzibar, lens, kms, events) do not depend on tokio at all: no tokio::spawn, no tokio::time, no block_on. A network task that panics fails only its own request; every completion a worker waits on carries a deadline; request context (identity, signing configuration, DAC bypass) travels with the task or message, never in a thread-local.

An on-demand runtime (two threads) starts only when a component needs network and was given no Edge: a build that starts no networking starts no runtime. The CLI starts one EdgeRuntime up front and passes it down.

Shutdown

One order, everywhere: stop accepting, drain in-flight requests with a deadline, stop the workers, close regolith, drop the runtime outside any async context.

Where the boundary sits

The edge is a router, not a worker: it terminates protocols, resolves remote inputs, picks the target worker once, and gets out of the way. The request chapter traces one request across it.

Why one runtime, passed in. Two failure modes the design refuses: a component that creates its own runtime (shutdown ordering becomes undefined, work continues after the server thinks it stopped) and ambient runtime capture (a library that only works inside a runtime, i.e. only inside someone else’s lifecycle). One handle, injected, is the same rule as the pool: ownership explicit, lifecycle singular.

One thread: wasm and single-core

The same code runs on one thread: the wasm main thread in the browser, or a single-core embedded target. This is not a degraded fallback; it is the same architecture with N = 1, and keeping it working is a design constraint that keeps the whole system honest.

The loop

One thread, one local executor running every task, one IoQueue:

  • A regolith call runs synchronous and inline on this thread.
  • A call that completes, completes; the task continues.
  • A commit helps every earlier commit itself: with one committer there is no other thread to wait for, so the committer drives the commit pipeline’s steps for the slots ahead of its own (the same helping protocol the multi-core path uses, just with one helper).
  • A call that needs I/O or stalls leaves a unit on this thread’s own IoQueue; the task awaits it; the thread runs another task.
  • When no task is ready, the thread polls its own queue with a budget: the WAL sync, queued block reads, and (in memory-env configurations with no worker) a flush or compaction step owed. Completions wake their tasks.

On wasm the pool runs “driven”: one worker on the caller’s thread, scheduled by the browser’s event loop; storage mounts OPFS, with durability falling back to eventual mode when the browser reports no durable sync.

Why this matters beyond wasm

The single-threaded path is the proof that nothing in the data path secretly requires a second thread: no Send bound, no blocking fallback, no “works with 16 cores” shortcut. Anything that would block the one thread (a blocking read, a lock on the data path, a spin) is visible here immediately, which is exactly why the discipline holds everywhere else.

Why one worker is a feature. An embedded target (a mobile app’s local store, an edge device) gets the full database: transactions, merges, ACP, replication over the same edge, on one core, because the design never bought throughput with a thread count.

Replication

Documents replicate as blocks, over two transport stacks behind one sync model. This part covers the transports, the push/pull mechanisms, and the discovery and admission machinery around them.

  • Transports and the peer: iroh/QUIC and libp2p, the endpoint task, the peer identity.
  • Push and pull: PushLog gossip, doc sync, DAG fetching, CAR transfer, and how merges run on the pool.
  • Providers, admission, budgets: signed service records, allowlists, inbound budgets, backpressure.

Transports and the peer

defradb.rs speaks two P2P stacks, feature-gated in one crate (crates/p2p):

  • iroh (QUIC): the default for defra-node, the CLI’s defra start, the embedded and FFI nodes, and the browser. One background task owns all iroh state and is commanded over a channel (crates/p2p/src/iroh/endpoint.rs); every Defra protocol, including gossip, is multiplexed over a single ALPN (with a v1 fallback), so there is one connection per peer, not one per subsystem. An optional self-hosted relay server exists for NAT traversal.
  • libp2p: a full swarm (gossipsub, kad, identify, relay, QUIC) used where the libp2p ecosystem is the deployment requirement. The standalone crates/bitswap (wantlists, ledgers, peer task queue) serves block fetches on this path.

Both stacks sit behind the same adapter surface, so the sync mechanisms, the read gate and the security model are shared. All P2P runs on the edge runtime (crates/defra-node/src/p2p_runtime.rs).

Peer identity

A node has one peer key (Ed25519, from the keyring: name peer-key), shared across transports; a node that predates the shared key keeps its existing identity. On iroh, the QUIC layer already authenticates the connection; on top of it, an optional Defra identity challenge binds the peer’s Defra DID to the connection (crates/p2p/src/peer_identity.rs).

The read gate

Replication carries data across a trust boundary, and gated access applies the same ACP read rules as a local query before a block is served (crates/p2p/src/bitswap/read_gate.rs, crates/db/src/block/verify.rs). Two deployment choices deliberately bypass the gate: an open Bitswap access mode serves without ACP checks, and a replicator registered for a collection without filters receives it; a filtered replicator’s access is checked against its filters. A peer with a connection is not a peer with permission where the gate applies: document-level ACP remains the authoritative boundary, and replicated blocks are checked (CID integrity, attached signatures) before merge.

Why one endpoint task. A shared socket must have one owner. Endpoint state scattered across tasks (each subsystem dialing its own connections) produces connection sprawl, races on migration, and no place to enforce admission. One task, one channel, one admission policy: the same ownership rule as the worker pool, at the network boundary.

Push and pull

Replication moves blocks (the DAG units), in three shapes.

Push: the PushLog

Local commits broadcast as signed PushLog messages over gossip topics (crates/p2p/src/sync/): per-collection and per-document topics, plus fixed topics for branchable sync and encryption-key distribution. A peer that receives a PushLog stores the blocks it carries, queues anything missing, and emits sync events; the DB-side merge runs on the pool, routed to the document’s worker with the same key affinity as a local write (crates/db/src/merge/pooled.rs).

Replicators are registered outbound replay targets: a durable intent to push a collection’s history to a specific peer, with filters (replication-filter). Push delivery is durable: durable delivery markers are written before the committing transaction reports success, and a persisted retry sweep (every 2 s) drains what the network missed.

Pull: doc sync and DAG fetch

  • Doc sync: a request for specific documents’ current heads and bodies over pubsub-RPC (bounded: at most 1000 IDs per request by default), served by the peer’s read-gated fetch handlers.
  • DAG sync: given a head, fetch the missing blocks: store what arrived, extract links, ask for what is missing (bitswap on libp2p; iroh streams with the same shape). Pending, partial DAGs live in a persisted pending store; a DAG whose root cannot eventually be resolved is quarantined (deterministic forensics, the PendingDagQuarantined event).
  • CAR transfer: a single-round-trip bounded DAG export/import (10,000 blocks, 16 MiB caps), with explicit authorization for what a CAR may contain.

A merge is admitted only once its blocks and KMS keys are local: the merge handler never reaches for the network mid-merge; remote inputs are resolved first (the doctrine again).

Backpressure

Everything inbound and outbound is bounded: concurrent DAG fetches and push tasks, push queue capacity in items and bytes, per-peer rate limits, inbound stream budgets (the next chapter). A slow peer slows itself, not the node.

Why push-and-pull instead of either alone. Push alone loses updates to partitions and late joiners; pull alone turns every write into a polling fan-out. Together: pushes propagate writes promptly to live peers; doc sync and DAG fetch repair gaps when peers (re)connect; durable delivery markers make push intent survivable across restarts. The trade is explicit: each mechanism is simple and bounded, and the composition is eventually consistent by construction (the DAG convergence models in proofs/).

Providers, admission, budgets

Provider discovery: signed service records

How do peers find who has what? Nodes publish service records: a signed, expiring statement of what this node offers (collections with roles Replica/Archive/Reader, replicator service, searchable-encryption query service, KMS, relay, custom roles), published via pkarr, served on query streams, and announced on a discovery topic (crates/p2p/src/iroh/records/). Readers keep the newest valid record per node in a book and pick fetch candidates and gossip neighbours from it. Record freshness, fan-in of replies, and the alternate-slot rule for the best provider are modelled: the provider record family has TLA+ and Lean proofs (see Verification).

Admission: who may connect

  • Allowlists (crates/p2p/src/iroh/endpoint_config.rs): AcceptAll (default) or an explicit endpoint set, mutable at runtime. Removing from the allowlist stops new admissions; PeerAdmission::revoke is the operation that actually bars a peer, and the admission authority makes revoke -> re-admit a lockstep state machine so a revoked peer cannot slip back in through a stale allowlist update.
  • Peer identity challenges (optional): bind the Defra identity to the connection.
  • Inbound budgets (crates/p2p/src/iroh/inbound_budget.rs): concurrent inbound streams are bounded; excess is refused, not queued unboundedly.

Trust and capability on the sync path

Replicator registration is outbound intent, not inbound permission: accepting PushLog data requires membership/subscription and explicit-replay authorization for the content; gated serving crosses the read gate (ACP) and block checks, while an open access mode or an unfiltered registered replicator is served without them. A separate capability regime governs explicit replay (re-broadcast of previously seen pushes), with its own revocation, modelled in crates/p2p/src/explicit_replay.rs.

Budgets, end to end

Backpressure is a property of the whole path, not a per-queue setting: bounded push queues (items and bytes), per-peer rate limits, bounded concurrent fetches, CAR caps (10,000 blocks / 16 MiB), doc-sync request caps (1000 IDs), pooled and persisted pending-DAG storage, and the retry sweep on a fixed interval. Overload at the network edge waits on a semaphore; overload inside the node surfaces as queue depth, never as unbounded memory.

Why signed, expiring records instead of a DHT of availability. A peer’s claim “I hold collection X” is useless if stale: the fetch fan-out burns a round trip per dead claim. Expiry forces re-assertion; signatures make records unforgeable (availability claims become attributable); and the book of newest-valid-records is small, local and cheap to consult, where a global availability index would be a coordination point the design does not otherwise need.

Lens Migrations

Schemas evolve; stored documents must not be rewritten to follow. A lens is a WASM module that transforms a document from one schema version to another, applied at query time (crates/lens): documents stay on disk in the version they were written in, and readers see them through the lens chain to the target version.

The pipeline

Given a collection’s version history (a DAG of schema versions), the lens history builder prunes it to one path per source version toward the target, and the pipeline applies the transform chain lazily: one document per next() call, on the caller’s task, inside the reader’s transaction (the lensed fetcher, crates/db/src/read/lensed/). Explicit migration runs (backfills) use the same pipeline; nothing is rewritten at migration-set time, so setting a migration is metadata, not a data rewrite.

The engine and the sandbox

One shared wasmtime LensEngine per database: one engine, one linker, one epoch clock; modules are compiled once at registration into an InstancePre, and each call instantiates and runs on a fiber the caller polls (crates/lens/src/engine/). The default transform store is restrictive-sandboxed WASM; without the wasmtime runtime feature, the store refuses everything (a build without lens support fails loud, not silently passing documents through).

The epoch tick

A lens module is untrusted code, so it runs under two bounds: fuel/ticks (a call out of ticks traps) and the epoch clock: EpochTick::tick() bumps the engine’s epoch, every running instance yields at its next check, and a module that exceeds its tick allowance traps deterministically. Tick sources: a periodic job on a worker pool’s deadline queue (PoolTicks), or, with no pool, a dedicated parked thread started on the first lens call (ThreadTicks) - a database that never runs a lens starts no thread.

Registration and use

Lens modules are registered over HTTP (POST /lens) and attached between versions (POST /lens/set or the collections migration route). At query time the lens runs for documents whose version differs from the target; explicit transactions pin their lens chain (PreparedLens) so a multi-statement transaction sees one consistent transform.

Why transform-on-read instead of rewrite-on-migrate. A rewrite is a full-dataset transaction: unbounded work, a fail window, and a rollback problem. Lenses avoid the rewrite entirely: setting a migration is metadata, every old version stays intact (time travel still works), and a bad migration is replaced (it is code, not data damage). The cost moves to the read path: each read of an old-version document transforms it through the chain, and repeated reads repeat that work, bounded per call by the epoch and fuel limits; an explicit backfill is the escape hatch when read cost matters.

Events

Clients consume change through subscriptions, and the ordering guarantee is the whole design: events are published in commit-receipt order (CommitReceipt.seq), the same order the engine made commits durable and visible. There is no separate sequencer to drift.

The bus

The event bus (crates/events) publishes named events: Update (a document create, update or delete, with the block payload), Merge / MergeComplete (replicated merges), peer and connection events, replicator completions, ACP height/cache events, quarantine events, and unique-index conflicts. Subscribers subscribe by name; GraphQL subscriptions are the client surface.

Events fire from ordered post-commit callbacks: the transaction registers an ordered on_commit hook, the engine’s receipt stream dispatches ordered callbacks in seq order across threads (crates/storage/src/backends/regolith/event_order.rs), and a discarded transaction publishes nothing. A commit’s events follow its durability, never precede it.

The two subscription shapes

  • The event stream (Update and friends): a revision stream for consumers that want every commit. Bounded channels; a shared dropped-counter; a non-zero check_and_reset_dropped() tells the client to resync rather than silently miss revisions.
  • Document change notifications: coalescing, lossless invalidation: one pending flag per document (swapped in one RCU), not a queue of revisions. A slow consumer gets “documents X, Y changed” once, not a backlog it cannot drain; it then re-reads. Capacity overflow sets resync_required, again visibly.

This split is deliberate: a projection builder wants the revision stream; a cache wants the invalidation signal. Forging a durable, gap-free stream of arrivals (as opposed to revisions) is the arrival journal, which clients consume by cursor rather than subscription.

P2P forwarding

Committed writes are handed to the replication broadcaster (push-to-replicators plus gossip): the broadcast marker is written durably, and only then does the committing transaction report success, so “committed” always implies “at least queued for replication” (see Push and pull).

Why receipt order and not wall-clock or per-source order. Two workers commit at the same microsecond on different cores: a timestamp cannot order them, and each source ordering them “itself first” is not an order at all. The commit receipt is the one sequence the engine already totally ordered, and ordering events by it makes the event stream a faithful log of what became visible, when, without a second coordinator to keep honest.

Memory Reclamation

defradb.rs holds a lot of derived data: every version of every field, index entries, blocks shared across documents, advisory counters. This chapter is how data leaves, how the concurrent machinery’s own memory is reclaimed, and how I/O is kept off the compute path - and why nothing leaves by accident.

No compaction filter, on principle

The engine offers a compaction filter (drop entries during SST compaction). defradb.rs installs none, and the reasoning is written beside the decision (crates/storage/src/backends/regolith/mod.rs):

  • a head-set entry’s meaning depends on writes that follow it;
  • nothing expires by time alone (a pending DAG record leaves when its root merges or is quarantined; downsample retention is cut from other keys);
  • a document part’s tombstone carries the priority a late replicated merge is ordered against - dropping it would resurrect deleted data;
  • index entries, blocks, ACP tuples and guards each decide something until another key says otherwise.

A filter that dropped any of them would change what a reader, or a later merge, sees. Retirement is a business decision with a policy behind it, and those run as ordinary transactions:

Block ownership

Blocks are shared: the same field block can back multiple documents’ histories. The systemstore keeps a CID -> DocID ownership map (/d/b/{cid}/{docID}), written at every create and merge. Deleting history removes ownership first (crates/db/src/block/cleanup.rs): a block’s bytes die only when its last owner mapping is gone and it is not reachable from anything retained. referenced_blocks computes the reachable set (commit + links + encryption links) of what stays; deletes keep blocks in that set even when their own owner is gone - the fix for the class of bug where pruning one document’s history pulled a block out from under another’s.

Downsample GC

Downsampled collections roll source documents into windowed targets; retention then prunes source history (crates/db/src/downsample/gc.rs):

  • plans are grouped per source; a source with any consumer lacking a retention policy is skipped entirely (never partially pruned);
  • a height is pruneable only when every plan for the source agrees (the intersection), and only below its retention cutoff;
  • current head CIDs are never pruned (they are the present, not history);
  • pruned composite commits lose their priority-index entries and their ownership, with field blocks deleted only when unreferenced by anything kept;
  • the whole prune is one transaction, discarded on error: a half-pruned history is never published.

Collection delete and truncate

Whole-collection removal walks the full reachable DAG and deletes unowned, unretained blocks (delete_owned_dag); truncate does the same filtered by a predicate. Index entries go page by page through the index manager.

Tombstones and markers

Deletion markers (d/del/) are read before materializing a document and survive until their history is pruned. LWW tombstones (empty bytes, priority intact) survive in the stored document for the same reason: a late merge from a replica must still lose to the delete.

The other reclamation: memory inside the concurrent machinery

The chapter so far reclaimed data. A lock-free system has a second, harder reclamation problem: the memory of its own concurrent structures. When several cores traverse a shared structure without locks, nobody may drop() or free() a node while another core may still hold a pointer to it - and knowing when no core does, without a lock, is the classical problem of wait-free programming.

defradb.rs’s answer is kovan, a wait-free memory reclamation library that the whole stack reaches through regolith::sync (kovan 0.1.x, with kovan-map, kovan-queue and kovan-channel beside it). Its shape:

  • A reader pins (one guard), loads pointers under the guard, and the guard keeps every loaded pointer valid until it drops. Read overhead is one atomic load and one comparison.
  • A writer that unlinks a value retires it: the value is freed only when no guard can still reach it. Reclamation is wait-free - pin, retire, guard drop and flush each complete in a bounded number of the caller’s own steps, whatever other threads (including stalled ones) do.
  • Memory is bounded: unlike epoch-based schemes, whose pending-retirement lists grow with the slowest thread, batches that cannot yet be placed are accumulated or adopted by other threads, never dropped and never unbounded, even across thread exit.
  • Retired nodes can be recycled through a free list (Reclaimable), so a structure that publishes one node per update allocates nothing in the steady state.

This is what sits under every Atom-swapped snapshot in the system. When the ACP policy snapshot publishes a new immutable policy table with one compare-and-swap, the old table’s memory is retired and freed by kovan exactly when the last reader’s guard drops - no reference-count handoff, no epoch thread, no lock. The same holds for the collections cache’s epoch-guarded swaps and the document-change coalescers in events. The maps and queues built on it (HopscotchMap per-core hash maps, ArrayQueue/SegQueue, the channels the inboxes use) inherit the same guarantee for every node they unlink. The reclamation protocol itself, and the maps, are modelled in TLA+ and Lean in kovan’s own proofs tree - the rule “no logic change without its models” holds one layer below this repository too.

One more reclamation loop, small and instructive: the async synchronization primitives (regolith::sync’s locks, semaphores, latches, notify) park a waiter node when a contended acquire suspends. Up to three parties may hold that node (the waiting future, the primitive’s queue, a wake list); each holds one reference bit in the node’s state word, and whichever party clears the last bit returns the node to its primitive’s node pool. No other path frees a node, so a node is never reachable by a party that has let it go - and, as the code beside it says, no epoch scheme is needed: reference bits plus a pool replace general-purpose reclamation for this one shape.

How I/O is separated from compute

Reclamation of waits follows the same separation as everything else in the threading model: I/O never runs on a data-path core, and a data-path core never blocks on I/O.

  • Every device operation is a unit on a per-thread IoQueue. A CacheOnly read miss or a pending commit ticket becomes a unit on the asking thread’s own queue; the completion arrives on that same queue, and only there (the worker pool). A busy core is never woken to service someone else’s completion, and no core ever waits for a lock held by a thread that is itself blocked on the device.
  • Units are claimable, single-flight. A block read is one unit no matter how many tasks await that block; a commit group’s fsync is one unit claimed by the first member core to poll. The memory bound follows: N waiters cost one in-flight device operation and N waiter nodes recycled through their pools.
  • Tasks wait; threads do not. Every wait in the data path is an .await on a future driven by the worker’s own waker: the task suspends, the core runs other work, the completion wakes exactly that task. The synchronization primitives themselves make no system call - no futex, no thread park, no clock read - so “waiting” costs a parked waiter node, not a kernel call.
  • Background I/O has its own threads. Compaction and log writeback, the only threads the engine starts, are placed by the pool as background-class threads, never on a caller’s core (LSM structure). In-memory environments start none and run compaction inline by necessity.
  • The network is one runtime away. Remote inputs are resolved at the edge before a transaction; a worker never holds memory waiting on the network mid-transaction, because the doctrine forbids the network inside the retried closure at all.

The memory-accounting consequence is the point of this section: because waits are per-task nodes (bounded, pooled, recycled by kovan and by the reference-bit scheme) rather than per-thread kernel waits, the system’s memory for concurrency is proportional to in-flight work, not to thread count or device latency.

Memory in the small

Reclamation of RAM follows the same bounded-by-design rules: iterators page by bytes and entries, streaming reads hold a page, caches are byte-bounded (the KMS tier, the vector code caches), the legacy-store rewrite copies in bounded batches, and the store’s statistics deliberately keep no histograms (the LSM chapter). The wasm and memory environments size to their profiles.

Why explicit ownership instead of refcounting or GC. Reference counting says “no one pointed at it at that instant”; replication makes that instant meaningless (a peer may re-deliver the block later). Ownership mappings are durable, replicated facts, pruned by transactions that validate what stays - so “may I delete this block?” is answered by the same machinery that answers every other question, and a wrong answer loses a commit instead of losing data.

API Surfaces

One database, several fronts. Each surface is a thin shell over the same core: the pool, the engine, the query pipeline.

HTTP (crates/http)

An axum server on the edge, with data-path routes moved onto the pool:

  • GraphQL at POST/GET /api/v0/graphql, subscriptions over the WebSocket /graphql/ws; Go-compatible API prefixes mounted beside the Rust ones.
  • Transaction routes (/tx): begin, commit, discard, in-transaction schema and document work (see Explicit transactions).
  • Collections REST: documents by DocID, describe, exists, versions, truncate; indexes (including Go-compatible encrypted indexes).
  • ACP: policy add/list/get/decide, relationships; NAC: enable, disable, admin.
  • P2P management: peers, connect, replicators, doc sync, relay.
  • Backup export/import (bounded), blocks (verify-signature), lens (register/set/reload), batch (BLS batch signing), views (+ refresh and GC), events (SSE), ccip (EIP-3668 reads), health, version, debug dump.

Auth: bearer-token middleware, per-route NAC permission mapping, optional TLS. Defaults: 127.0.0.1:9181, 300 s timeout, bounded concurrency.

CLI (crates/cli)

defra starts a node (HTTP, optional pg-compat, iroh or libp2p, keyring-backed keys, optional at-rest encryption, Vera or local ACP) and carries a full HTTP client surface (defra client ...: acp, backup, blocks, collections, documents, graphql, indexes, lens, p2p, txns, views), plus keyring, identity and SDL utilities.

Embedded (crates/embedded, crates/defra-node)

Two builders: defra-node (the newer, minimal builder: pool, optional network edge started only if needed, background tasks) and embedded (the older embedder API with transport and ACP configuration). Both place the store on a pool (storage::start_pool) and expose the same DB core; a node with no network starts no network runtime.

FFI (crates/ffi)

A C ABI static library matching Go’s cbindings/: node lifecycle, schema, documents, queries and subscriptions, transactions, blocks, batch, backup, lens, indexes, ACP (DAC and NAC), P2P. Panics are captured per call and returned as results, never unwound across the boundary. For Go and mobile embedders.

pg-compat (crates/pg-compat)

A Postgres wire-protocol server: accepts psql connections, translates SQL to the query engine (DDL, DML, joins, aggregates, expressions, parameters), on the edge runtime. Existing SQL tooling works against defradb.rs without a new driver.

Around the surfaces

  • Orbis (crates/orbis): a gRPC client for threshold BLS document signing by an Orbis ring (the M6 milestone of the KMS plan); used for BLS-augmented batch signatures.
  • KMS (crates/kms): the key management service milestone set: a key store over durable IPLD blocks, an in-memory byte-bounded tier, remote single-flight batched key fetch over the P2P encryption topic, and the NAC/DAC dual gate for key release (document-scoped keys need DAC read; collection-scoped need NAC permission). Wire-compatible with Go’s KMS.
  • Telemetry (crates/telemetry): OTLP trace/metrics export behind a feature; always-on process counters (retries, conflicts by layer, storage events, engine tickers as one OTel counter family).

Why thin shells. Every behavioural rule this book describes (ordering, ACP, pooling, prepared inputs) is implemented once, under the core. A surface that grew its own semantics would be a second database with worse tests; the HTTP layer, the CLI, the FFI, the SQL bridge and two embedders all deliberately share one.

Verification

defradb.rs carries its correctness argument beside the code, in two tools (proofs/README.md):

  • TLA+ / TLC for temporal, distributed and concurrent behaviour: convergence, “eventually merges”, safety under adversarial interleavings. 52 models live in proofs/tla/, each with GREEN configurations and, for every guard, a RED configuration that plants a named bug and must fail on its named invariant. Each TLC run finishes in under 60 seconds; the whole suite in under 10 minutes.
  • Lean 4 for functional and algebraic properties: CRDT merge laws (commutativity, associativity, idempotence, order-independence), encodings and round-trips, data structure invariants (proofs/lean/). No sorry, no admit, no new axioms.

Some theorems need both halves: DAG convergence = (TLA+: every node eventually receives every delta under eventual connectivity) x (Lean: applying deltas in any order yields the same state). Neither half alone is convergence.

The rules of engagement

  • The model ships with the change, and before the code: a spec is the contract; a model that does not pass means the design is broken, and the code waits.
  • A model names the Rust code it models (file and function) and is wired into the proof runner’s registry; a model that no longer matches the code is a defect.
  • Proof files read ELI5: every line of spec carries a plain-words comment, every invariant opens with a one-sentence statement of its promise, every RED config says which bug it plants.

The honest gaps

The coverage map also records the backlog: engine OCC is an implementation boundary; HeadSet.tla models derived head keys and scan/write conflicts, not collection-version validation; remote ACP/Vera check paths, dynamic KMS policy changes, and cold read-time decryption remain audit gaps. The inventory says so in the same table as the coverage, because a proof map that hides its holes is a falsified map.

Why models at all, for a database. The properties that matter here - convergence under reordering, no public ACP window, exactly-once registration, dense arrival prefixes, no lost commit after a fence - are exactly the class testing cannot establish: a test shows one interleaving is fine; a model checker shows all of them are, within each model’s configured bounds and assumptions (small bounded instances, assumed connectivity and fairness; a green run is not an unbounded deployment guarantee). And the RED configurations are the part that keeps the greens honest: a guard that cannot be broken on purpose is a guard nobody understands.
